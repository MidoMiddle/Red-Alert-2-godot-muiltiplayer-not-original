## 1. Цель и результат

**Цель:** два и больше игроков на разных компьютерах (macOS и Windows) играют одну партию скирмиша через интернет без проброса портов, без рассинхронов и с ощущением отклика как в одиночной игре.

**Что будет работать в конце вехи:**

1. Проект `Rts.Net`: детерминированный lockstep поверх надёжного UDP (LiteNetLib).
2. Игра по локальной сети / по IP: один игрок создаёт игру (хост), другие подключаются.
3. Игра через интернет через ретранслятор `Rts.Server` — никаких открытых портов у игроков.
4. Предстартовая проверка: версия игры, версия симуляции, хеш данных, хеш карты.
5. Общий seed и синхронная загрузка: партия начинается одновременно у всех.
6. Адаптивная задержка ввода по пингу, индикатор «ожидание игрока».
7. Обнаружение рассинхрона по контрольным суммам, дамп состояния, инструмент сравнения дампов.
8. Обработка вылета игрока, правила паузы, сохранение повтора при обрыве.
9. Сетевой симулятор (задержка, джиттер, потери) для тестов.
10. CI-тест: один и тот же повтор на macOS, Windows и Linux даёт одинаковые контрольные суммы.

**Как это выглядит для игрока:** в главном меню пункт «Сетевая игра» → «Создать» или «Подключиться по адресу / коду». Простое лобби (полноценное — в M10), кнопка «Старт», и партия идёт у всех одинаково. Если у друга пропал интернет, на экране появляется «Ожидание игрока Петя… 12 с», потом — либо продолжение, либо «Игрок покинул игру».

## 2. Рамки

### Входит

- `Rts.Net`: протокол, сериализация сетевых сообщений, lockstep-движок, адаптивная задержка.
- Транспорт: LiteNetLib (надёжный упорядоченный канал + ненадёжный канал для пингов).
- Режим 1: прямое подключение (хост = один из игроков) — LAN и по IP.
- Режим 2: ретранслятор в `Rts.Server` (комната = одна партия, сервер только пересылает).
- Предстартовое рукопожатие, seed, синхронная загрузка.
- Контрольные суммы, обнаружение и разбор рассинхрона, `tools/Rts.DesyncDiff`.
- Вылет и возвращение в рамках таймаута, пауза, «сдаться».
- Повтор сохраняется у каждого клиента, в том числе при обрыве.
- Минимальное сетевое лобби в клиенте: слоты, фракция, цвет, команда, готовность (без аккаунтов).
- Сетевой симулятор и интеграционные тесты.
- Кросс-платформенный тест детерминизма в CI.

### Не входит (и в какой вехе появится)

| Что | Где |
|---|---|
| Аккаунты, список комнат, чат лобби, приглашения по ссылке | M10 |
| Матчмейкинг по рейтингу, рейтинг | M10 |
| Хранение повторов на сервере, сайт | M10 |
| Переподключение к идущей игре после таймаута (догон состояния) | После M10 (см. открытые вопросы) |
| Наблюдатели | После M10 |
| NAT-пробивка (прямое P2P через интернет) | Не планируется — используем ретранслятор |
| Голосовой чат | Не планируется |

## 4. Технические решения

### 4.1. Модель: детерминированный lockstep с задержкой ввода

- Каждый клиент считает всю симуляцию сам (M0). По сети идут только команды.
- Тик `T` можно посчитать, только когда получены **пакеты команд всех активных игроков** на тик `T` (даже пустые).
- Команда, отданная игроком на локальном тике `T`, планируется на тик `T + D`, где `D` — задержка ввода в тиках.
- Отображение отклика (голос, маркер приказа) — мгновенно, локально, без ожидания исполнения.

**Почему не клиент-сервер с авторитетным сервером:** сервер должен был бы считать симуляцию (дорого) и передавать состояние сотен юнитов (трафик). Lockstep передаёт единицы КБ/с при любом числе юнитов — так работали RA2 и StarCraft.

### 4.2. Транспорт: LiteNetLib

| Критерий | LiteNetLib |
|---|---|
| Лицензия | MIT — совместима с GPL-3.0 |
| Платформы | Чистый C#, работает на macOS/Windows/Linux и в Godot .NET |
| Каналы | Надёжный упорядоченный, надёжный неупорядоченный, ненадёжный |
| Прочее | Встроенные пинг/RTT, таймауты, симуляция задержки и потерь (используем как дополнение к нашему `SimulatedTransport`) |

**Каналы:**

| Канал | Режим | Что идёт |
|---|---|---|
| 0 | Надёжный упорядоченный | Рукопожатие, лобби, старт, `TickBundle`, контрольные суммы, системные события |
| 1 | Ненадёжный | Пинг-понг для оценки RTT и джиттера |

Вся логика работает через `ITransport` — LiteNetLib можно заменить, не трогая lockstep.

### 4.3. Топология

| Режим | Как | Когда |
|---|---|---|
| **Прямой (хост)** | Один из игроков — хост: принимает подключения и рассылает пакеты остальным. Логически это тот же ретранслятор, только внутри клиента | LAN, тесты, игра по IP с открытым портом |
| **Ретранслятор** | `Rts.Server` на VPS. Все клиенты подключаются к серверу, сервер пересылает пакеты внутри комнаты | Основной режим игры через интернет |

Оба режима используют **один и тот же код ретрансляции** (`RelayRoom`) — в прямом режиме он запускается внутри клиента хоста.

**Сервер не считает симуляцию** и не проверяет игровую логику. Он проверяет только формат сообщений, принадлежность игрока комнате и частоту сообщений.

### 4.4. Протокол

Общий заголовок каждого сообщения:

```
u8   messageType
u16  protocolVersion
...  тело
```

| Сообщение | Направление | Тело |
|---|---|---|
| `Hello` | клиент → хост/сервер | gameVersion (строка), simVersion u32, dataHash u64, playerName, roomCode (для ретранслятора) |
| `Welcome` / `Reject` | хост → клиент | playerSlot / причина отказа |
| `LobbyState` | хост → все | слоты: игрок, фракция, страна, цвет, команда, стартовая позиция, готов; карта и её хеш; опции |
| `LobbyChange` | клиент → хост | изменение своего слота |
| `StartGame` | хост → все | seed u64, settings (как в повторе M0), mapHash u64, начальная задержка D |
| `LoadProgress` | клиент → все | процент загрузки |
| `AllLoaded` | хост → все | тик 0 можно начинать |
| `TickBundle` | клиент → все (через хост/сервер) | playerId, tick, команды (формат M0) |
| `Checksum` | клиент → все | tick, hash u64 |
| `Ping` / `Pong` | все | timestamp (только для RTT, в симуляцию не попадает) |
| `PauseRequest` / `Pause` / `Resume` | клиент ↔ хост | кто, причина |
| `PlayerLeft` | хост → все | playerId, причина, тик выхода |
| `Surrender` | клиент → все | — (это ещё и обычная команда симуляции) |
| `DesyncReport` | клиент → хост | tick, свой hash |

**Важно:** выход и поражение игрока, влияющие на игру, оформляются **как команды симуляции** с номером тика (`PlayerLeftCommand`, `SurrenderCommand`), чтобы все клиенты применили их на одном и том же тике.

### 4.5. Пакеты тиков (`TickBundle`)

```
u8   messageType = TickBundle
i32  playerId
i32  tick                  — для какого тика команды
u16  commandCount          — 0 = пустой пакет («мне нечего сказать»)
...  команды в формате M0 (u8 type, i32 player, i32 executeTick, u32 sequence, payload)
```

- Каждый игрок отправляет **ровно один** `TickBundle` на каждый тик, даже пустой. Пустой пакет = подтверждение «я дошёл до этого тика, команд нет».
- **Пакетирование:** при 15 тиках/с пакеты отправляются каждый тик (≈15 сообщений/с на игрока, по 10–30 байт). Если в будущем станет много — объединяем несколько тиков в одно сообщение (поле `tickCount`), формат готов к этому.
- Команды внутри тика у всех применяются в порядке `(PlayerId, Sequence)` — как в M0, поэтому порядок прихода пакетов не важен.

### 4.6. `LockstepEngine`: когда считать тик

```
каждый кадр:
    отправить свой TickBundle для тика (текущий + D), если ещё не отправлен
    пока есть пакеты всех активных игроков на тик currentTick
         и не превышен лимит тиков за кадр:
        собрать команды тика, simulation.Step()
        currentTick++
    если не хватает пакетов дольше порога → показать «ожидание игрока»
```

- **Буфер:** клиент заранее держит пакеты на `D` тиков вперёд — это и есть запас против джиттера.
- **Догон:** если клиент отстал (например, после фризa), он считает несколько тиков за кадр (лимит 5 из M0, в сети — до 10), пока не догонит.
- **Скорость игры** в сетевой партии фиксируется хостом при старте (меняется только паузой).

### 4.7. Адаптивная задержка ввода (`InputDelayController`)

- Пинг-понг по ненадёжному каналу 4 раза в секунду → RTT и джиттер (скользящее среднее и максимум за 5 с).
- Требуемая задержка: `D = ceil((maxRTT / 2 + jitter + запас) / длительность_тика)`, минимум 2 тика, максимум 10.
- Задержку определяет **хост** (по худшему игроку) и рассылает её изменение **как команду** с номером тика, начиная с которого действует новое `D` — так все меняют её синхронно.
- Изменение не чаще раза в 2 секунды и не больше чем на 1 тик за раз — чтобы не было рывков.

| RTT (худший) | D при 15 тиках/с | Задержка приказа |
|---|---|---|
| ≤ 40 мс | 2 | ~133 мс |
| 100 мс | 3 | ~200 мс |
| 150 мс | 4 | ~267 мс |
| 300 мс | 6 | ~400 мс |

Задержка до ~250 мс в RTS не ощущается благодаря мгновенному локальному отклику (голос, маркер).

### 4.8. Предстартовые проверки

| Проверка | Как | Если не совпало |
|---|---|---|
| Версия протокола | `protocolVersion` в каждом сообщении | Отказ: «несовместимая версия сети» |
| Версия игры | Строка из сборки | Отказ: «обновите игру» |
| Версия симуляции | `simVersion` из M0 | Отказ |
| Хеш данных | Хеш YAML-данных из `Rts.Data` (M3) | Отказ: «данные игры отличаются» |
| Хеш карты | Хеш карты из M7 | Пока — отказ «у вас нет этой карты» (передача карт — открытый вопрос) |

### 4.9. Seed и синхронный старт

1. Хост генерирует `seed` (из системного ГСЧ — это вне симуляции, допустимо) и рассылает его в `StartGame` вместе с настройками.
2. Все клиенты загружают карту, ассеты и создают симуляцию с одинаковыми настройками.
3. Каждый присылает `LoadProgress`; экран загрузки показывает прогресс всех игроков.
4. Когда все на 100 % — хост рассылает `AllLoaded`; тик 0 начинается у всех.
5. Таймаут загрузки — 120 с, потом медленный игрок исключается до старта.

### 4.10. Контрольные суммы и рассинхрон

- Каждые **N = 15 тиков** (раз в секунду) клиент отправляет `Checksum(tick, hash)` от `StateHasher` (M0).
- Хост (или каждый клиент — в ретрансляторе это проще) сравнивает суммы всех игроков на этом тике.
- **Расхождение = рассинхрон:**
  1. Игра ставится на паузу у всех, сообщение «Рассинхронизация на тике N».
  2. Каждый клиент сохраняет **дамп** (`StateDump`): полное состояние симуляции на тике N в текстовом виде (сущность за сущностью, поле за полем, детерминированный порядок) + повтор до тика N.
  3. Файлы кладутся в `user://desync/<дата>_<tick>/`.
  4. Партия завершается без результата (в M10 — не влияет на рейтинг).
- **`tools/Rts.DesyncDiff`:** берёт два дампа → выводит первую расходящуюся сущность и поле. Второй режим: берёт повтор, прогоняет его до тика N headless и сравнивает с дампом — помогает понять, у кого из двух игроков ошибка.
- **Режим отладки:** суммы на каждом тике + «хеш по подсистемам» (отдельно юниты, здания, экономика, ГСЧ) — сразу видно, какая подсистема разошлась.

### 4.11. Вылет игрока

| Ситуация | Поведение |
|---|---|
| Пакеты не приходят > 3 с | Индикатор «Ожидание игрока X… (N с)» у всех, игра стоит |
| Нет пакетов > 30 с или соединение закрыто | Хост объявляет `PlayerLeftCommand` на тике T+D |
| После выхода | Игрок считается **проигравшим**; его здания и юниты **остаются на карте** под управлением нейтрального «пустого» владельца и не действуют (как в RA2), союзник **не** получает контроль |
| Голосование «исключить» | Через 10 с ожидания любой игрок может нажать «Исключить» — исключение после согласия большинства оставшихся |
| Вылетел хост (прямой режим) | Партия завершается (миграция хоста — не делаем; ретранслятор решает проблему) |

**Решение по умолчанию** (предлагается к согласованию): вышедший = поражение, его объекты остаются неактивными. Это просто, честно и не ломает баланс 2×2.

### 4.12. Пауза

- Каждый игрок может поставить паузу **3 раза за партию**, максимум **60 с** каждая (в лобби можно отключить).
- Снять паузу может только тот, кто поставил, или любой — после истечения 60 с.
- Пауза — команда симуляции с номером тика, тикам симуляции она не мешает (в паузе тики просто не идут).

### 4.13. Повторы в сети

- Каждый клиент пишет повтор локально (`ReplayRecorder` из M0) — все команды всех игроков + контрольные суммы.
- В заголовок повтора добавляются: список игроков, фракции, цвета, хеш карты, версия игры.
- При обрыве / рассинхроне / выходе — повтор сохраняется до последнего посчитанного тика.
- Загрузка повторов на сервер — M10.

### 4.14. Ретранслятор (`Rts.Server`, часть M9)

- Консольное .NET-приложение, запускается в Docker на VPS.
- **Комната** = код из 6 символов (без похожих букв: `0/O`, `1/I`), создаётся первым клиентом, живёт до конца партии + 60 с.
- Сервер пересылает сообщения внутри комнаты; хостом лобби считается создатель комнаты.
- **Ограничения:** не более 8 игроков на комнату; не более 60 сообщений/с от клиента; не более 4 КБ на сообщение; лимит комнат с одного IP.
- **Нагрузка:** на партию 4 игрока ≈ 4 × 15 × 30 байт ≈ 2 КБ/с — один дешёвый VPS держит сотни партий.
- Логи: создание/завершение комнат, отказы, рассинхроны (без содержимого команд).

### 4.15. Сетевой симулятор (`SimulatedTransport`)

- Реализация `ITransport` в памяти, без сокетов.
- Параметры на каждое направление: задержка (мс), джиттер (мс), потери (%), дублирование (%), обрыв в заданный момент.
- Детерминированный (свой seed) — тест падает воспроизводимо.
- Позволяет в одном процессе запустить 2–8 «клиентов» с отдельными симуляциями и проверить, что контрольные суммы совпадают.

### 4.16. Интеграция с клиентом Godot

- `NetGameHost` заменяет локальный цикл `SimulationHost` (M0) в сетевой партии: источник команд — `LockstepEngine`, а не прямой ввод.
- Сетевой поток LiteNetLib опрашивается в `_Process` главного потока (`PollEvents`) — никакой многопоточности в обработке команд.
- Экраны: «Сетевая игра» (создать / подключиться по IP / по коду комнаты), «Сетевое лобби» (минимальное), оверлей ожидания, экран рассинхрона.

### 4.17. Кросс-платформенный тест в CI

- В репозиторий кладутся **эталонные повторы** (`tests/replays/*.rtsreplay`): 2–3 партии бот против бота по 10 минут, с разными фракциями и картами.
- Задача CI `determinism` на macOS, Windows и Linux: проигрывает каждый повтор headless и сравнивает контрольные суммы с записанными в файле.
- Плюс: суммы трёх ОС сравниваются между собой в отдельном шаге (артефакты задач).
- Эталонные повторы перегенерируются осознанно при изменении правил симуляции (повышается `simVersion`).

## 5. Шаги реализации

| № | Шаг | Результат | Готово, когда |
|---|---|---|---|
| 1 | **Каркас `Rts.Net`** | Проект, `ITransport`, сообщения, reader/writer | Тесты сериализации всех сообщений туда-обратно |
| 2 | **`SimulatedTransport`** | Транспорт в памяти с задержкой/потерями | Тест: сообщения доходят с заданной задержкой, надёжный канал не теряет и не переставляет |
| 3 | **Lockstep в памяти** | `LockstepEngine`, `TickBundle`, пустые пакеты | 2 симуляции в одном процессе через `SimulatedTransport`, 5000 тиков, суммы совпадают при 0 мс и при 150 мс ± 50 мс, 2 % потерь |
| 4 | **Рукопожатие и старт** | `Handshake`, `StartGame`, seed, `LoadingBarrier` | Тесты: несовпадение каждой версии/хеша даёт отказ; старт у всех на одном тике |
| 5 | **Контрольные суммы и рассинхрон** | `ChecksumExchange`, `DesyncDetector`, `StateDump` | Тест: искусственная порча состояния у одного клиента → рассинхрон обнаружен на ближайшей проверке, дампы записаны |
| 6 | **`Rts.DesyncDiff`** | Консольный инструмент | На дампах из шага 5 показывает испорченную сущность и поле |
| 7 | **Адаптивная задержка** | `InputDelayController`, синхронное изменение D | Тест: при росте RTT D растёт, изменение применяется у всех на одном тике, суммы совпадают |
| 8 | **LiteNetLib** | `LiteNetTransport`, пинг | Две копии клиента на одном Mac играют через localhost |
| 9 | **Прямой режим в клиенте** | Меню «Сетевая игра», минимальное лобби, `NetGameHost` | Партия Mac ↔ Mac по LAN до победы одного из игроков |
| 10 | **Вылет и пауза** | Ожидание, исключение, `PlayerLeftCommand`, пауза | Ручные сценарии раздела 7 проходят; тесты на таймауты в симуляторе |
| 11 | **Повторы в сети** | Расширенный заголовок, сохранение при обрыве | Повтор сетевой партии проигрывается в клиенте с совпадением сумм |
| 12 | **Ретранслятор** | `Rts.Server` с `RelayRoom`, Dockerfile | Партия через сервер на localhost; затем через VPS из двух разных сетей |
| 13 | **Mac ↔ Windows** | Сборка Windows, игра через ретранслятор | Партия 20+ минут Mac ↔ Windows без рассинхрона |
| 14 | **CI детерминизма** | Эталонные повторы, задача `determinism` на трёх ОС | Зелёный CI |
| 15 | **Закрытие вехи** | Документация, PR | Все критерии раздела 7 |

## 6. Тесты

### Модульные (`Rts.Net.Tests`)

| Область | Что проверяем |
|---|---|
| Сообщения | Сериализация туда-обратно для каждого типа; отказ на обрезанных и слишком больших сообщениях |
| `TickBundle` | Пустой пакет; порядок команд не важен; дубликат пакета игнорируется |
| `LockstepEngine` | Не считает тик без пакетов всех игроков; догоняет после задержки; соблюдает лимит тиков за кадр |
| `InputDelayController` | Формула D; гистерезис (не дёргается); границы 2…10 |
| `Handshake` | Каждое несовпадение → свой код отказа |
| `DesyncDetector` | Совпадение / расхождение; несколько игроков; суммы, пришедшие в разном порядке |

### Интеграционные (через `SimulatedTransport`)

| Сценарий | Ожидание |
|---|---|
| 2 игрока, 0 мс | Суммы совпадают 10 000 тиков |
| 4 игрока, 150 ± 50 мс, 2 % потерь | Суммы совпадают; ни одного зависания дольше D тиков |
| Задержка растёт 50 → 300 мс | D растёт, суммы совпадают |
| Один игрок замолкает на 5 с | Остальные ждут, потом продолжают с тем же результатом |
| Один игрок пропадает | Через 30 с `PlayerLeftCommand`, игра продолжается у остальных, суммы совпадают |
| Порча состояния у одного | Рассинхрон на ближайшей проверке, дампы созданы |
| Боты в сетевой партии | 2 бота у разных «клиентов» → суммы совпадают (проверка детерминизма `Rts.AI`) |

### Сервер (`Rts.Server.Tests`)

- Создание и закрытие комнат, код комнаты уникален.
- Пересылка только внутри комнаты.
- Ограничения: частота, размер, число игроков, комнаты с одного IP.

### Кросс-платформенные

- Эталонные повторы на macOS/Windows/Linux в CI (4.17).
- Ручная партия Mac ↔ Windows через ретранслятор (раздел 7).

## 7. Критерии готовности вехи (Definition of Done)

**Автоматические:**
- [ ] Все тесты `Rts.Net.Tests` и `Rts.Server.Tests` зелёные.
- [ ] Интеграционные сценарии из раздела 6 зелёные.
- [ ] CI `determinism` зелёный на macOS, Windows, Linux.
- [ ] `Rts.Net` и `Rts.Server` собираются без предупреждений.

**Ручная проверка:**
- [ ] Партия Mac ↔ Mac по LAN через прямой режим до конца.
- [ ] Партия Mac ↔ Windows через ретранслятор на VPS, 20+ минут, без рассинхрона.
- [ ] Партия 2×2 (два человека + два бота) через ретранслятор.
- [ ] Отключение сети у одного игрока на 10 с → «ожидание», потом продолжение.
- [ ] Отключение навсегда → через 30 с игрок выбывает, игра продолжается.
- [ ] Пауза, лимит пауз, снятие паузы.
- [ ] Несовпадение версии / данных / карты → понятное сообщение, а не вылет.
- [ ] Повтор сетевой партии проигрывается локально с совпадением сумм.
- [ ] Искусственный рассинхрон (отладочная клавиша) → пауза, сообщение, дампы, `Rts.DesyncDiff` находит причину.
- [ ] Ощущение отклика при пинге 100–150 мс не хуже одиночной игры (голос и маркер — мгновенно).

**Документация:**
- [ ] [11_multiplayer.md](../11_multiplayer.md) актуализирован (решения по вылету, паузе, задержке).
- [ ] Описан протокол (раздел 4.4) как отдельный справочник `docs/formats/net_protocol.md` (или в этом документе).
- [ ] Инструкция: как развернуть ретранслятор на VPS.
- [ ] Статус M9 — «готово».

## 8. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Скрытый недетерминизм всплывает только в сети (Mac vs Windows) | Высокая | Эталонные повторы в CI с M5–M8 заранее; хеш по подсистемам; `Rts.DesyncDiff` |
| Боты недетерминированы между клиентами | Средняя | Бот работает внутри симуляции (M5); интеграционный тест «боты в сетевой партии» |
| Ощущение лага при большом пинге | Средняя | Мгновенный локальный отклик; адаптивная D; честный индикатор пинга |
| Один медленный компьютер тормозит всех | Средняя | Лимит догоняющих тиков; показ «у игрока X низкая производительность»; профилирование симуляции |
| LiteNetLib ведёт себя иначе в Godot на Windows | Низкая | Транспорт за `ITransport`; ранняя проверка на шаге 8–13 |
| Злоупотребления ретранслятором (флуд) | Средняя | Ограничения частоты, размера, комнат с IP; логи |
| Дампы рассинхрона огромные | Низкая | Текстовый формат с сжатием; только при рассинхроне |

## 9. Открытые вопросы

1. **Вышедший игрок:** поражение и неактивные объекты (рекомендация) — или передача юнитов союзнику в командной игре?
2. **Передача карт:** если у игрока нет карты хоста — отказ (рекомендация для M9) или автоматическая передача карты (≤ 1 МБ) через сеть?
3. **Переподключение после таймаута** (догон через повтор с ускоренной симуляцией): делать после M10 или не делать вовсе?
4. **Максимум игроков:** 8 (как в RA2) — достаточно?
5. **Миграция хоста** в прямом режиме — не делаем (рекомендация), прямой режим остаётся для LAN.
