## 1. Цель и результат

**Цель:** превратить сетевую игру из M9 («подключись по коду») в онлайн-сервис: аккаунты, лобби со списком комнат и чатом, приглашения, рейтинг, история матчей, повторы и сайт, с которого игру можно скачать.

**Что будет работать в конце вехи:**

1. **Аккаунты:** регистрация и вход (email + пароль и вход через Discord), один аккаунт для игры и сайта.
2. **Онлайн-лобби** в игре: список открытых комнат, создание комнаты, слоты (фракция, страна, цвет, команда, позиция), готовность, чат комнаты, кик хостом.
3. **Приглашения:** код комнаты и ссылка-приглашение, открывающая игру сразу в комнате.
4. **Ретранслятор M9** встроен в сервис: партия из лобби стартует через него автоматически.
5. **Рейтинг 1×1** (Glicko-2), результаты матчей фиксирует сервер.
6. **Матчмейкинг 1×1:** кнопка «Найти соперника» подбирает игрока близкого рейтинга (последний этап вехи).
7. **Повторы на сервере:** автоматически загружаются после партии, скачиваются с сайта, открываются в игре.
8. **Сайт:** главная со скачиванием для Mac и Windows, профили, история матчей, таблица лидеров, страница матча, список изменений.
9. **Инфраструктура:** один VPS, Docker Compose, HTTPS, резервные копии, мониторинг, защита от злоупотреблений.
10. **Приватность:** политика конфиденциальности, удаление аккаунта, экспорт своих данных.

**Как это выглядит для игрока:** заходит на сайт → скачивает игру → регистрируется (или «Войти через Discord») → в игре «Онлайн» → видит комнаты → заходит или создаёт свою, кидает другу ссылку → играет → после партии его рейтинг меняется, матч появляется в профиле на сайте, повтор можно скачать.

## 2. Рамки

### Входит

- `Rts.Server`: сервис лобби, аккаунтов (API), матчей, рейтинга, повторов + ретранслятор из M9.
- Сайт на том же стеке.
- База данных PostgreSQL, миграции.
- Клиент: экраны входа, онлайн-лобби, комнаты, чата, матчмейкинга, просмотра профиля (минимально — остальное на сайте).
- Развёртывание: Docker Compose на одном VPS, обратный прокси с HTTPS, резервные копии, мониторинг, логи.
- Приватность и безопасность: хеширование паролей, ограничения запросов, модерация (бан, мут), политика конфиденциальности.

## 4. Технические решения

### 4.1. Стек сервера и сайта

| Часть | Выбор | Почему |
|---|---|---|
| Язык | **C# / .NET** | Один язык с игрой; общие DTO и проверка повторов через `Rts.Simulation` |
| Веб-фреймворк | **ASP.NET Core** | Зрелый, быстрый, встроенные аутентификация, rate limiting, WebSocket |
| Сайт | **Razor Pages** (серверный рендер) | Простые страницы без отдельного фронтенд-проекта и сборки JS; SEO из коробки |
| Реальное время (лобби, чат) | **WebSocket** (ASP.NET Core) | Двусторонний канал, просто использовать из Godot (`WebSocketPeer`) или из C# (`ClientWebSocket`) |
| Партия | **UDP-ретранслятор из M9** (LiteNetLib) | Уже есть; низкая задержка |
| БД | **PostgreSQL** + **EF Core** (миграции) | Стандарт, надёжно, бесплатно |
| Прокси, HTTPS | **Caddy** | Автоматические сертификаты Let's Encrypt, простой конфиг |
| Развёртывание | **Docker Compose** на одном VPS | Один файл, легко повторить и восстановить |

**Почему один процесс** (API + сайт + WebSocket + UDP): на старте нагрузка мала, так проще разворачивать и отлаживать. Код разделён по модулям, так что при росте ретранслятор можно вынести в отдельный процесс без переделки.

### 4.2. Аккаунты и вход

**Рекомендация: email + пароль и вход через Discord** (Discord — естественная площадка для сообщества RTS).

| Механизм | Решение |
|---|---|
| Пароли | ASP.NET Core Identity, хеш PBKDF2 (по умолчанию Identity) |
| Подтверждение email | Письмо со ссылкой; без подтверждения нельзя играть рейтинговые |
| Восстановление пароля | Письмо со ссылкой (срок жизни 1 час) |
| Discord | OAuth 2.0 (scope `identify`, `email`) |
| Сессия на сайте | Cookie (HttpOnly, Secure, SameSite=Lax) |
| Сессия в игре | Вход через браузер: игра открывает страницу входа, получает **токен устройства** по одноразовому коду (как «вход на телевизоре»). Пароль в игру не вводится |
| Токен в игре | Долгоживущий refresh-токен (90 дней) + короткий access-токен (1 ч), хранится в `user://` |
| Ник | Уникальный, 3–16 символов, латиница/цифры/`_`, смена раз в 30 дней |
| Отправка писем | Внешний SMTP-сервис (транзакционные письма) |

**Почему вход через браузер:** игра никогда не видит пароль, Discord-вход работает без встроенного браузера, и это стандартная безопасная схема для десктопных клиентов.

### 4.4. Онлайн-лобби

**Протокол лобби** — JSON-сообщения по WebSocket (`Rts.Online.Contracts`):

| Сообщение | Кто | Что |
|---|---|---|
| `room.list` / `room.list.update` | клиент ↔ сервер | Список открытых комнат с фильтрами (карта, игроки, ранговая/нет) |
| `room.create` | клиент | Карта, макс. игроков, пароль (опц.), видимость (открытая / по ссылке) |
| `room.join` / `room.leave` | клиент | По id или коду |
| `room.state` | сервер | Полное состояние: слоты, игроки, боты, карта, опции, готовность |
| `room.slot.update` | клиент | Своя фракция/страна/цвет/команда/позиция; хост — боты и закрытие слотов |
| `room.ready` | клиент | Готов / не готов |
| `room.kick` | хост | Исключить игрока |
| `room.start` | хост | Все готовы → сервер создаёт `match`, комнату ретранслятора и рассылает параметры старта (seed, адрес, токен комнаты) |
| `chat.message` | клиент ↔ сервер | Чат комнаты (и общий чат хаба — опционально) |

- **Сервер — источник правды** для лобби (в отличие от M9, где хостом был клиент): цвета не повторяются, слоты валидны, карта существует.
- После `room.start` клиенты подключаются к ретранслятору M9 с **токеном комнаты**; дальнейший протокол партии — из M9 без изменений.
- **Приглашения:** код комнаты (6 символов, из M9) и ссылка `https://<домен>/join/<код>`. Ссылка открывает страницу, которая запускает игру через схему URL `rtsgame://join/<код>` (регистрируется при установке) или показывает код для ручного ввода.

### 4.5. Результаты матчей

- Каждый клиент по окончании партии отправляет **отчёт**: id матча, итог по каждому игроку, последний тик, финальная контрольная сумма.
- Сервер принимает результат, если отчёты **согласованы** (одинаковые итоги и финальная сумма у большинства).
- **Спорные случаи** (отчёты расходятся, рассинхрон, все вышли): матч помечается `desync` / `abandoned`, рейтинг не меняется; повтор сохраняется для разбора.
- **Выход из партии** = поражение (решение M9) — и в рейтинге тоже.
- **Позже (опционально):** серверная проверка спорных матчей — сервер проигрывает загруженный повтор headless через `Rts.Simulation` и определяет победителя. Архитектура это позволяет (повтор + та же симуляция).

### 4.6. Рейтинг: Glicko-2

**Рекомендация: Glicko-2, а не Elo.**

| Критерий | Elo | Glicko-2 |
|---|---|---|
| Учитывает уверенность в рейтинге | Нет | Да (deviation) — новички быстро находят свой уровень |
| Неактивные игроки | Рейтинг «замораживается» | Неуверенность растёт со временем |
| Сложность | Проще | Немного сложнее, но алгоритм хорошо описан |
| Где используется | Шахматы (классика) | Многие современные онлайн-игры |

- Стартовые значения: rating 1500, deviation 350, volatility 0.06.
- Обновление сразу после каждого ранкового матча (без «периодов»).
- **Видимый рейтинг** = `rating − 2 × deviation` (консервативная оценка), чтобы новички не взлетали в топ после пары побед.
- Таблица лидеров: минимум 10 игр и deviation < 150.
- Расчёт рейтинга — на сервере, в `double` (это вне симуляции, детерминизм тут не нужен).

### 4.7. Матчмейкинг 1×1

- Очередь: игрок нажимает «Найти соперника», выбирает фракцию (или случайно) и пул карт.
- Подбор раз в 2 секунды: пары с минимальной разницей рейтинга; допустимая разница растёт со временем ожидания (±100 → ±400 за 2 минуты).
- Учитывается пинг до ретранслятора (не ставим вместе игроков с суммарным RTT > 300 мс).
- Найденная пара → автоматически создаётся закрытая комната → старт после подтверждения обоими (15 с).
- Отказ от подтверждения — штраф: блок очереди на 1, 5, 15 минут.

### 4.8. Повторы на сервере

- После партии клиент загружает повтор (`.rtsreplay`) через HTTP API (один загрузивший достаточно; остальные пропускают, если хеш совпал).
- Хранение: файловая система VPS (`/data/replays/<год>/<месяц>/<match_id>.rtsreplay`), размер — десятки КБ.
- Лимиты: 1 МБ на повтор, хранение **1 год**, потом удаляются (кроме матчей топ-100).
- Скачивание: с сайта (страница матча) и из игры («Мои матчи»).

**Политика версий повторов** — рекомендация:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Хранить все старые версии симуляции в клиенте | Любой повтор проигрывается | Клиент растёт, старый код поддерживать сложно |
| **Помечать «устарел» + архив сборок** (рекомендация) | Простой клиент | Старый повтор смотрится только в старой версии |

Реализация: повтор с `simVersion` ≠ текущей помечается на сайте «записан в версии X.Y»; рядом ссылка на архивную сборку этой версии (GitHub Releases). Клиент при открытии такого повтора показывает понятное сообщение со ссылкой.

### 4.10. Безопасность и защита от злоупотреблений

| Угроза | Защита |
|---|---|
| Перебор паролей | Rate limiting на вход (5 попыток/мин на IP и аккаунт), блокировка на 15 мин |
| Массовые регистрации | Rate limiting, подтверждение email, капча — только если начнутся проблемы |
| Флуд в чате | Лимит 1 сообщение/с, мут на время, фильтр длины |
| Флуд комнатами | Не больше 1 открытой комнаты на аккаунт |
| Подделка результата | Согласованность отчётов (4.5), повтор как доказательство |
| Токсичность | Жалоба на игрока из лобби/после партии, бан/мут модератором (роль в БД) |
| SQL-инъекции, XSS, CSRF | EF Core (параметризованные запросы), Razor (экранирование), антифорджери-токены ASP.NET Core |
| Утечка секретов | Секреты только в переменных окружения на сервере, не в репозитории |

### 4.11. Приватность (основы GDPR)

- Собираем минимум: email, ник, Discord id (если вход через Discord), IP в логах (хранится 30 дней), данные матчей.
- **Политика конфиденциальности** на сайте: что собираем, зачем, сколько храним, как удалить.
- **Удаление аккаунта:** личные данные удаляются, в истории матчей ник заменяется на «Удалённый игрок».
- **Экспорт данных:** кнопка в настройках аккаунта → JSON со всеми своими данными.
- Cookies — только необходимые (сессия), без аналитики третьих сторон → баннер согласия не нужен.

### 4.12. Инфраструктура

| Элемент | Решение |
|---|---|
| VPS | 2 vCPU, 4 ГБ RAM, 80 ГБ диск, Linux; ориентир $5–10/мес |
| Контейнеры | `server` (Rts.Server), `postgres`, `caddy`, `backup` |
| Домен | ~$10/год; DNS A-запись на VPS |
| HTTPS | Caddy + Let's Encrypt, автоматическое продление |
| Порты | 443 (HTTPS + WebSocket), UDP-порт ретранслятора |
| Резервные копии | `pg_dump` каждую ночь + папка повторов; хранение 14 дней локально + копия во внешнее хранилище |
| Восстановление | Инструкция в `deploy/README.md`, проверка восстановления раз в месяц |
| Мониторинг | Проверка доступности снаружи (`/health`), метрики (онлайн-игроки, комнаты, партии, ошибки) на странице администратора, оповещение в Discord-канал при падении |
| Логи | Структурированные логи в файл с ротацией, 30 дней |
| Обновление | Сборка образа в CI (GitHub Actions) → `docker compose pull && up -d` на сервере |

### 4.13. Клиент

- `OnlineClient`: HTTP (вход, профиль, загрузка повторов) + WebSocket (лобби, чат, матчмейкинг) + переход к M9 при старте партии.
- Работа с сетью — асинхронно, но все изменения состояния UI и игры — в главном потоке Godot.
- Экраны: вход (через браузер), хаб онлайна (комнаты, кнопка матчмейкинга, ник и рейтинг), комната (слоты, чат, готовность), поиск соперника, итоги партии с изменением рейтинга.
- Совместимость версий: при подключении сервер сообщает минимальную поддерживаемую версию; старый клиент видит «Обновите игру» и ссылку.

## 6. Тесты

### Модульные

| Область | Что проверяем |
|---|---|
| Glicko-2 | Эталонные примеры из описания алгоритма; ничья; неактивность увеличивает deviation |
| Матчмейкинг | Расширение окна рейтинга со временем; учёт пинга; нет пары с самим собой |
| Лобби | Уникальность цветов; валидность слотов; права хоста; переход хоста при выходе |
| Результаты | Согласие / расхождение / неполные отчёты → правильный статус |
| Приглашения | Код уникален, без похожих символов; истёкший код |

### Интеграционные (WebApplicationFactory + PostgreSQL в контейнере)

- Регистрация → подтверждение → вход → токен устройства → обновление токена.
- Полный цикл: два клиента → комната → старт → результаты → рейтинг → повтор доступен.
- Rate limiting: перебор пароля блокируется; флуд в чате мутится.
- Удаление аккаунта: личные данные удалены, матчи остались с «Удалённый игрок».
- Миграции применяются на пустой и на заполненной БД.

### Нагрузочные (простые)

- 200 одновременных WebSocket-подключений к лобби, 50 одновременных партий через ретранслятор на целевом VPS — без деградации.

### Ручные

- Вход через Discord, восстановление пароля, письма.
- Сайт на телефоне.
- Приглашение по ссылке на Mac и Windows.

## 8. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Безопасность аккаунтов (утечка, взлом) | Средняя | Identity, rate limiting, секреты вне репозитория, обновления зависимостей, минимум личных данных |
| Подделка результатов ради рейтинга | Средняя | Согласованность отчётов; повтор как доказательство; позже — серверная проверка повтора |
| Сервер — единая точка отказа | Средняя | Бэкапы, инструкция восстановления, мониторинг; прямой режим M9 работает без сервера |
| Расходы растут | Низкая | Lockstep-трафик крошечный; повторы маленькие и с ограниченным сроком хранения |
| Юридические требования к персональным данным | Средняя | Минимум данных, политика, удаление и экспорт с первого дня |
| Регистрация схемы `rtsgame://` отличается на Mac и Windows | Средняя | Проверить на шаге 10; запасной путь — ввод кода вручную |
| Малое число игроков → матчмейкинг пустой | Высокая | Лобби и приглашения — основной путь; матчмейкинг последним шагом; кооп против ботов как режим |
