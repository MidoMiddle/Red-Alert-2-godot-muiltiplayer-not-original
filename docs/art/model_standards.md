# Стандарт моделей

> Статус: действует · Создан: 2026-10-25
> Родительские документы: [M1: стандарты моделей (4.7) и пайплайн (4.8)](../implementation/M1_visual_spike.md) · [Требования к генерации элементов карты](../map_elements/generation_requirements.md)

Как сделать модель и подключить её к игре. Правила генерации (промты, сервисы, бюджеты элементов карты, стиль) — в [generation_requirements.md](../map_elements/generation_requirements.md). Здесь — то, что нужно, чтобы модель встала в игру.

---

## 1. Как модель попадает в игру

Модель — это только внешний вид. Игровой объект (что это, сколько HP, кому мешает) уже есть в данных или в симуляции, а модель «натягивается» на него по таблице.

1. Положить файл: `game/assets/models/<папка>/<id>/<файл>.glb`.
2. Дописать строку в таблицу моделей [`game/data/visuals/models.yaml`](../../game/data/visuals/models.yaml).
3. Проверить в галерее моделей. Каждая модель стоит на плите своего футпринта, клетки видны:

   ```bash
   /Applications/Godot_mono.app/Contents/MacOS/Godot --path game -- --ui-units --models
   ```

4. Записать файл в [реестр ассетов](../assets_registry.md).

Если объекта нет в таблице или файла нет на месте, рисуется заглушка (warning в логе, игра работает).

Модель, сделанную скриптом Blender (`tools/blender/`), не правим руками: правки вносим в скрипт и запускаем его заново. Раскладка исходника, `bake/` и `.glb` — в [assets_src/models/README.md](../../assets_src/models/README.md).

Новый игровой объект нужен, только если вещь **ведёт себя** по-новому: новый юнит, здание или объект карты со своими правилами. Например, пальма в пустыне — это то же «дерево» (`pine_tree`), только другой формы, и новый объект ей не нужен.

## 2. Таблица моделей

Файл `game/data/visuals/models.yaml`, формат `models/1`. Одна строка — одна модель:

```yaml
format: models/1
models:
  building/neutral_smokestack: { file: industrial/smokestack/smokestack.glb, height: 6 }
  tree/palm:                   { file: desert/palm/palm_01.glb, scale: 1.2, yaw: 45 }
  object/snowdrift:            { file: map/snowdrift_01/snowdrift_01.glb, climates: [winter] }
```

### Несколько разновидностей одной модели

Если у объекта несколько моделей (пять кактусов, два сугроба, три домика одного типа), вместо `file` пишем `files` со списком:

```yaml
tree/cactus: { files: [desert/cactus/cactus_01.glb, desert/cactus/cactus_02.glb, desert/cactus/cactus_03.glb,
                       desert/cactus/cactus_04.glb, desert/cactus/cactus_05.glb], jitter: 0.15, spin: true }
```

- **Выбор по клетке.** Каждый объект получает модель из списка по своей клетке. Расчёт постоянный: одно и то же дерево всегда тот же кактус, после перезапуска и в повторе тоже. Соседи получают разные модели, а по карте разновидности распределяются поровну.
- **Здание** выбирает по своей северо-западной клетке, **дерево и объект карты** — по клетке, где стоят.
- **Юнит** — по порядку, в каком создаются виды юнитов. Это только внешний вид.
- **Новая разновидность.** Чтобы добавить шестой кактус, допишите файл в список. Если какого-то файла нет, он пропускается с предупреждением, остальные рисуются.
- **`jitter`** — разброс размера каждой копии, например 0,15 = ±15 %.
- **`spin: true`** — каждая копия повёрнута как угодно. С поворотом и разбросом даже два-три файла выглядят как разные деревья. Для зданий и заборов `spin` не ставим: у них есть лицевая сторона и направление.
- **На игру не влияет.** Выбор, размер и поворот только визуальные, симуляция их не видит.

### Ключи

| Ключ | Что рисует | Где взять id |
|---|---|---|
| `building/<id>` | здание игроков или здание карты | `game/data/factions/*/buildings*.yaml`; нейтральные и тех-здания — `neutral_*`, `tech_*` (`BuildingTypes.cs`) |
| `unit/<id>` | юнит | `game/data/factions/*/units*.yaml` |
| `object/<id>` | объект карты | `MapObjectTypes.cs`: `boulder`, `fence_wood`, `wall_stone`, `lamp_post`, `anti_tank_hedgehog`, `pipeline`, `snowdrift`, `ore_source` и мелочь из документов элементов — `bench`, `phone_booth`, `beach_umbrella`, `hay_bale`, `well`, `barbed_wire` и другие (заглушки — [PropLooks.cs](../../game/scripts/Terrain/PropLooks.cs)) |
| `tree/<форма>` | дерево по климату (и маскировка Mirage Tank) | `pine` (снег), `broadleaf_small` и `broadleaf_big` (умеренный, город), `palm` и `cactus` (пустыня) |
| `ore/<вид>` | кластеры руды на поле | `ore`, `gems` |

К любому ключу можно дописать `@<климат>`: `building/neutral_house_a@urban` — модель того же здания на картах этого климата. На такой карте она рисуется вместо модели ключа без климата, на остальных — модель без климата. Так у городских карт свои дом и многоэтажка при тех же данных игры. Климат — имя папки в `game/data/climates/`.

Деревья на карте — это один объект `pine_tree`. Форму выбирает климат, поэтому деревья подключаются ключом `tree/<форма>`, а не `object/pine_tree`.

### Поля

| Поле | По умолчанию | Смысл |
|---|---|---|
| `file` | — | путь от `game/assets/models/`, строчные буквы, `.glb` |
| `files` | — | список таких путей — разновидности модели, до 64; нужен `file` или `files`, не оба |
| `jitter` | 0 | разброс размера каждой копии в обе стороны, 0…0,5 |
| `spin` | false | каждая копия повёрнута как угодно |
| `scale` | 1 | масштаб, 0,01…100. Нужен, только если модель сделана не в масштабе 1 клетка = 1 единица |
| `height_scale` | 1 | сжатие только по высоте, 0,1…10; футпринт не меняется. У гражданских зданий карты, сделанных «этаж на клетку», стоит 0,35 — так они низкие, как в RA2 |
| `yaw` | 0 | поворот вокруг вертикали в градусах, −360…360 |
| `offset` | `[0, 0, 0]` | сдвиг в клетках `[x, y, z]` |
| `height` | 0 | высота здания в клетках: на ней полоски здоровья и значки (ремонт, нет энергии). При 0 берётся высота заглушки |
| `climates` | все | список климатов, где модель рисуется: `winter`, `temperate`, `urban`, `desert`. В остальных климатах — заглушка |
| `damaged`, `damaged_occupied`, `occupied`, `abandoned`, `ruins` | — | файлы того же здания (`building/<id>`) в его состояниях: повреждено (от четверти до половины здоровья), повреждено и занято пехотой, целое и занято пехотой, покинуто (меньше четверти здоровья, пехота вышла), руины на месте упавшего. Без поля рисуется основной файл |

Неизвестное поле или ключ — ошибка с номером строки. Тест `ModelTableTests` проверяет, что каждый файл таблицы существует и каждый ключ называет объект игры.

## 3. Единицы, оси, точка опоры

| Параметр | Стандарт |
|---|---|
| Формат | glTF 2.0 бинарный (`.glb`) |
| Масштаб | **1 клетка = 1 единица.** Здание 2×2 занимает ровно 2×2 единицы. Юниты — в пропорциях RA2 (замер по зданиям RA2, 2026-10-26): средний танк ≈ 1,1 клетки в длину и ≈ 0,85 в ширину, харвестер ≈ 1,4 в длину, пехотинец ≈ 0,6 клетки в высоту. Гражданские здания RA2 низкие: этаж ≈ 0,25 клетки (≈ 0,4 пехотинца), офис в 4 этажа ≈ 1 клетка, двухэтажный дом с крышей ≈ 0,8; высотки остаются высокими. Корабли и авиация — так же крупнее прежнего, ×1,4. Модели, сделанные раньше по старому стандарту (танк 0,8, пехотинец 0,5), показываются с `scale: 1.4` в таблице моделей |
| Оси | +Y вверх, «перёд» смотрит в **−Z** (стандарт Godot; экспорт из Blender с `export_yup`) |
| Трансформации | применены: масштаб 1, поворот 0 |
| Точка опоры | **здание** — центр футпринта, низ подложки на земле (раздел «Фундамент» ниже); **юнит** — центр основания на земле; **объект карты, дерево** — центр клетки на земле; **кластер руды** — центр клетки |
| Футпринт | здание не выходит за свой футпринт по X и Z (его размер в клетках — в данных здания). Подложка может выступать за стены, но не больше чем на 0,06 клетки |

Камера RA2 стоит на юго-востоке: поворот 45° по горизонтали, наклон 30° вниз ([RtsCamera.cs](../../game/scripts/Camera/RtsCamera.cs)). Видны южная (+Z) и восточная (+X) стороны, поэтому лицевую сторону здания (ворота, двери) ставим на +Z. Клетка выхода завода и клетка разгрузки перерабатывающего завода лежат с юга от футпринта.

Объекты, которые идут цепочкой (забор, труба), рисуются секцией вдоль оси X. Каменная стена и пролёты моста пока не подключены: им нужна ориентация по соседям, это следующий шаг.

### Фундамент

Здание не ставится прямо на землю или песок. Под стенами у него бетонная подложка, узел `base`: так видно фундамент, а не что здание просто стоит на грунте. Правило относится ко всем зданиям: гражданским, промышленным, техздания и здания карты.

- **Обычное здание** (дом, многоэтажка, цех, котельная) — бетонная плита по контуру стен. Её край не дальше 0,06 клетки за стеной, высота 0,12–0,2 клетки. Бетон серый, по тону отличается от стен, без цвета команды. У трубы и градирни постамент или плита с ограждением выше: это часть их силуэта.
- **Здание на опорах** (бак на ножках, качалка) — бетонная плита под опорами, внутри футпринта. Опоры стоят на бетоне, а не на земле.
- **Руины** — подложка остаётся на месте разрушенного здания: это то, что осталось от фундамента.
- **Хижина** (условная, например будка ремонта моста 1×1) — без бетона. Под ней участок земли, чуть другого оттенка, чем земля вокруг; на песке — участок песка другого оттенка. Это тонкая плита `base` толщиной 0,01–0,02 клетки, чуть над землёй, чтобы не мерцала с ландшафтом. Оттенок берём из палитры климата ([03_environment.md](style_guide/03_environment.md), раздел 2).

Проверка — пункт в [чек-листе стайлгайда](style_guide/07_review_checklist.md), раздел 1: подложка видна у каждой модели в галерее `--ui-units --models`.

## 4. Части модели (имена узлов)

| Узел | Где нужен | Что делает игра |
|---|---|---|
| `team_mask` | здания игроков, техника, захватываемые тех-здания | все меши внутри узла с этим именем (или с именем, начинающимся с `team_mask`) красятся в цвет владельца |
| `turret` | техника и корабли с башней | поворачивается к цели независимо от корпуса. Опорная точка — в оси вращения |
| `hull` | техника | корпус: поворачивается вместе со всем юнитом |
| `barrel`, `muzzle_0..N` | оружие | ствол и точки выстрела (пустые узлы); эффекты выстрела подключим позже |
| `drill` | буровая руды (`object/ore_source`) | вращается и красится в цвет руды или самоцветов |
| `fire_1…N` | здание, которое горит (почти разрушено) | пустые узлы: в них игра ставит пламя (частицы); дым идёт над крышей. Без них пламя над крышей |
| `base` | здания и объекты карты: бетонная подложка (раздел «Фундамент» выше), плита под опорами бака и качалки | пока только для читаемости; игра её не трогает |
| `gate` | заводы: откидные ворота | когда из завода выходит юнит, игра опускает ворота наружу, держит открытыми 2,5 с и поднимает ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)). Опорная точка узла — петля внизу ворот; ворота открываются в сторону своей +X, поворачиваясь вокруг своей Z (Godot), на 85°. Лёгшие ворота не выходят за футпринт |
| `spin_*` | здания: радар, вентилятор | игра вращает узел вокруг его оси Y (1,2 рад/с), пока здание достроено и у владельца хватает энергии ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)). Опорная точка узла — на оси вращения |
| `arm` → `arm_upper` → `arm_fore` | ремонтный цех: манипулятор, узлы вложены друг в друга | пока цех ремонтирует (`RepairSystem.IsRepairing`), игра качает основание вокруг его Y, плечо и предплечье вокруг их Z, каждый от позы модели; после ремонта рука плавно возвращается в позу ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)). Опорная точка каждого узла — в его шарнире |
| `crane` → `cable`, `hook` | ремонтный цех, верфь: кран, трос и крюк под ним | пока здание ремонтирует или строит то, что умеет строить (верфь — корабли), игра качает кран вокруг его Y и опускает-поднимает крюк; трос, висящий от своей точки вдоль −Y, растягивается до крюка ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)). Опорная точка крана — на оси мачты, троса и крюка — на конце стрелы |
| `roller_gate`, `carriage`, `crate`, `hoist_cable`, `hoist_hook`, `hatch_a`, `hatch_b`; метки `carriage_out`, `hoist_grab`, `hoist_drop` | стройплощадка: цикл постройки | пока владелец строит здание или оборону, игра крутит 8-секундный цикл: ворота сворачиваются вверх (масштаб `roller_gate` по Y, опорная точка вверху проёма), каретка выезжает к метке `carriage_out`, захват опускается до `hoist_grab` и поднимает ящик, каретка возвращается, створки люка (`hatch_a` вокруг X на −85°, `hatch_b` на +85°, опорные точки в петлях) открываются, захват опускает ящик до `hoist_drop`, люк и ворота закрываются. Начатый цикл доигрывается до конца ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)) |
| `shroud` → `shroud_a`, `shroud_b`, метка `shroud_open`; `rocket`, метка `rocket_up` | ракетная шахта | пока ракета готова (заряд супероружия полон), шахта открыта: кожух `shroud` поворачивается на 45° вокруг Y, половины разъезжаются (`shroud_a` к метке `shroud_open`, `shroud_b` настолько же в другую сторону), ракета поднимается к метке `rocket_up`; всё за 4 с. После пуска ракета сразу пропадает, шахта закрывается, внутри появляется опущенная ракета ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)) |
| `dome`, `drum` | хроносфера | пока заряд супероружия полон, игра за 2 с поворачивает подвижную половину купола `dome` вокруг её X на −90° (опорная точка — шарнир у основания на длинной оси) и раскручивает барабан `drum` вокруг его X; после применения барабан останавливается, купол закрывается ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)) |
| `glow_sphere` | железный занавес: шар | пока заряд супероружия полон, шар раскаляется: за 3 с его своя копия материала наливается красным свечением, потом свечение пульсирует; после применения шар остывает ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)) |
| `turret` → `gatling_*` | оборона: поворотная турель и блоки стволов | пока у обороны есть цель, игра поворачивает `turret` вокруг Y к цели (4 рад/с; перёд турели — её −Z, опорная точка на оси поворота) и раскручивает узлы `gatling_*` вокруг их Z; без цели стволы плавно останавливаются, турель остаётся как стояла ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)) |
| `join_n`, `join_e`, `join_s`, `join_w` | стена игрока: полустенки от центрального столба к краям клетки | игра показывает только те, что смотрят на соседнюю клетку со стеной того же владельца (север — клетка y−1, в Godot −Z), так протянутая линия срастается в сплошную стену; одиночный сегмент — только столб ([PlayerBuildings.cs](../../game/scripts/Terrain/PlayerBuildings.cs)). Красная полоса на полустенке — узел `team_mask_*` под ней |
| `body`, `roof`, `chimney` … | части зданий и объектов карты | пока только для читаемости; анимации — позже |

Цвет команды сейчас ставится на весь узел `team_mask` сплошным цветом. Шейдер с маской в канале текстуры по M1 (4.6) — следующий шаг. Тогда эта строка изменится, а имя узла останется.

## 5. Материалы, текстуры, бюджет

- PBR: albedo, normal, ORM (occlusion, roughness и metallic в одной текстуре).
- Текстуры: 512² — мелкие объекты на одну клетку, 1024² — техника и средние объекты, 2048² — большие здания. В исходниках PNG, Godot сжимает сам.
- Не больше двух материалов на модель: так дешевле рисовать пачками (деревья, сугробы, заборы рисуются через MultiMesh).
- Свет и тени не запекаем. Свечение — emissive-материал.
- Треугольники (LOD0): пехота ≤ 1 500, техника ≤ 8 000, здания ≤ 20 000, мелкие объекты ≤ 1 000, средние ≤ 3 000; деревья и кактусы ≤ 300, пни ≤ 100 (ниже).

### Деревья: лес на карте

Решение владельца 2026-10-28. Дерево — самый массовый объект карты, поэтому его бюджет в десятки раз меньше, чем у техники.

**Откуда числа.** На dense-taiga 12 048 деревьев на карте и ещё около 13 800 на кайме за её краем — 25 829 (замер командой `heavy`, 2026-10-28). Примитивы сейчас тратят по 132 треугольника на дерево, вся сцена — 4,9 млн. В кадре при обычном приближении около 1,5 тыс. деревьев; с тенями каждое рисуется дважды. При 3 000 треугольников на дерево это около 9 млн треугольников за кадр, при 300 — меньше 1 млн.

| Что | Бюджет | Правило |
|---|---|---|
| Дерево и кактус (LOD0) | ≤ 300 | ель, лиственное, пальма, кактус — всё, чем климат рисует дерево карты |
| Дерево вдали (LOD1) | около 50 % | Godot строит его при импорте (`Generate LODs` не выключать) |
| Пень | ≤ 100 | появляется только у срубленного дерева; под живым деревом заранее не ставится |
| Дерево каймы | ≤ 50 или картинка (импостор, 2 треугольника) | кайма за краем поля — больше половины деревьев карты, с ней не играют |
| Тень дерева | от упрощённой формы | карта теней получает простой силуэт (конус, шар), а не саму модель |

- Крона — цельная геометрия, без листьев-картинок с прозрачностью: прозрачность заставляет видеокарту перерисовывать одни и те же пиксели и стоит дороже лишних треугольников.
- Генераторы дают в десятки раз больше: модель уменьшаем в Blender (decimate) до бюджета, а мелкие ветки убираем совсем — с высоты камеры их не видно.

## 7. Временные модели по мотивам RA2

Решение владельца (2026-10-28). Пока игра в разработке, модели юнитов и зданий делаем **похожими на RA2**, но не копиями один в один. Игрок, который знает RA2, должен с первого взгляда понимать, что перед ним: казарма, военный завод, тесла-катушка, «Киров». Потом, когда будет готова своя модель, она заменит временную под тем же ключом в [таблице моделей](../../game/data/visuals/models.yaml). Код и данные при этом не меняются.

### Что берём у RA2

- **Назначение и признаки назначения.** У казармы флаг, вход в рост человека и плац. У военного завода широкие ворота, из которых выезжает техника. У очистительного завода есть бункер для руды и площадка, куда встаёт харвестер. У электростанции градирни или трубы.
- **Силуэт и пропорции.** Низкое и широкое здание, высокая башня, длинный корпус — как в RA2. Масштаб такой же относительно клетки и соседних построек.
- **Главную деталь, по которой юнит или здание узнают.** У тесла-катушки витая катушка с шаром наверху. У призменной башни кристалл на мачте. У «Кирова» сигарообразная оболочка с гондолой. У «Апокалипсиса» две пушки и четыре гусеницы. У «Носорога» тяжёлый корпус с одной толстой пушкой.
- **Рабочие места модели.** Ворота, док, выход пехоты, ствол и башня стоят там, где их ждёт механика игры: там же, где в RA2.
- **Сторону.** Союз — тяжёлый бетон и сталь, угловатые коробки. Альянс — светлые панели и аккуратные формы. Цвет команды — на тех же крупных частях.

Ориентир — файл `appearance.md` юнита или здания (`docs/ra2_units/`, `docs/ra2_buildings/`): там словами описано, как оно выглядит в RA2.

### Что делаем сами

- **Геометрию.** Модель собирается в Blender с нуля, скриптом (`tools/blender/`), по описанию из `appearance.md`.
- **Детали, панели, текстуры и материалы.** Мелочь, которая не нужна для узнавания, — наша.

### Чего не берём и временно

- **Файлы RA2:** воксели, спрайты, текстуры, иконки. Их нет в репозитории и в сборках ([15_legal](../15_legal.md), раздел 1).
- **Обводку по скриншоту.** Скриншот или рендер RA2 не кладём подложкой в Blender и не переносим контуры точь-в-точь.
- **Надписи, логотипы, эмблемы сторон RA2.**
- **Лица героев.** Таню узнают по снаряжению, позе и оружию, Юрия — по одежде и силуэту. Лицо персонажа не копируем.
- **Название RA2 в промте генератора.** Генератор по такому промту выдаёт копию; описываем словами из `appearance.md`.

### Как помечаем

- **В [реестре ассетов](../assets_registry.md)** в колонке «Лицензия» пишем: «собственная работа проекта; временная, по мотивам RA2». По этой пометке собирается список на замену.
- **Перед публичным релизом** все модели с этой пометкой заменяются своим дизайном ([15_legal](../15_legal.md), раздел 6).

### Проверка

Модель показываем владельцу в галерее (`--ui-units --models`) без подписи. Он называет, что это. Не узнал — модель доделывается.
