## 1. Цель и результат

**Цель:** до начала основного геймплея проверить главный риск проекта — **сможем ли мы получить картинку уровня «ремастера RA2»** с помощью Godot, AI-генераторов 3D и Blender-скриптов. Если не сможем — узнаём это сейчас, а не после полугода работы над механиками.

**Что будет работать в конце вехи:**

1. Камера ровно под углом RA2: клетка выглядит ромбом 2:1, ортографическая проекция, скролл и небольшой зум.
2. Зимняя сцена: рельеф из сетки, плавное смешивание снега, травы, грязи и дороги, деревья (инстансинг), мелкие декорации.
3. 2–3 здания и 2 танка, полученные через пайплайн «AI-концепт → AI-3D → Blender-скрипты → glTF → Godot», с цветом команды.
4. Свет, мягкие тени, SSAO, цветокоррекция через LUT — настройки «зимнего» климата.
5. Тестовые юниты M0 отображаются моделями танков вместо кубиков, ездят по клику, как в M0.
6. Сравнительный скриншот нашей сцены рядом с референсом «RA2 2000 vs 2026».
7. Начат реестр ассетов: у каждого файла — источник и лицензия.

**Как это выглядит для игрока:** заснеженная окраина базы — несколько зданий, дорога, ели, два танка разных команд. Клик — танк едет. Геймплея нет, но кадр уже похож на игру.

**Новой игровой логики нет.** Симуляция — из M0. M1 меняет только отображение, контент и инструменты.

## 4. Технические решения

### 4.1. Камера RA2

**Геометрия угла.** Нужно, чтобы квадратная клетка на земле выглядела ромбом с соотношением сторон 2:1.

- Поворот камеры вокруг вертикали (**yaw**) — **45°**: стороны клетки идут по диагоналям экрана.
- Наклон (**pitch**, угол над горизонтом) — **30°**. Обоснование: горизонтальная диагональ ромба не зависит от наклона, а вертикальная умножается на `sin(pitch)`. Соотношение 2:1 требует `sin(pitch) = 0,5`, то есть ровно **30°**. (Классическая «изометрия» 35,26° дала бы соотношение √3:1 — не как в RA2.)
- Проекция — **ортографическая** (`Camera3D.Projection = Orthogonal`).

| Параметр | Значение |
|---|---|
| Yaw | 45° |
| Pitch | 30° (камера смотрит вниз под 30° к горизонту) |
| Проекция | Ортографическая |
| Размер (`Size`) по умолчанию | Подбирается так, чтобы при 1080p клетка занимала ~60 пикселей по ширине (как в RA2 при 1024×768, но с учётом Retina) |
| Зум | `Size` от 0,7× до 1,6× от значения по умолчанию, плавно |
| Near / Far | Камера отнесена на 100 единиц, `Far` с запасом под высоты и здания |

**Устройство:** `CameraRig` (Node3D, двигается по плоскости земли) → `Pivot` (поворот yaw/pitch) → `Camera3D` (отнесена назад). Скролл двигает только `CameraRig` по XZ, угол никогда не меняется.

**Скролл:**

| Способ | Поведение |
|---|---|
| Края экрана | Полоса 8 пикселей, скорость растёт к краю |
| Стрелки / WASD | Постоянная скорость, с ускорением при удержании |
| Перетаскивание правой кнопкой | Как в RA2: смещение пропорционально отклонению от точки нажатия |
| Колесо мыши | Зум |

Скорость скролла задаётся в клетках/сек и одинакова на любом зуме по ощущению (масштабируется с `Size`). Камера ограничена прямоугольником карты с отступом.

**`RtsCamera.ScreenToGround(Vector2)`** — луч из камеры в плоскость земли (а после появления рельефа — пересечение с мешем по сетке высот). Используется вводом из M0.

### 4.2. Масштаб и координаты в Godot

| Величина | Значение |
|---|---|
| 1 клетка | **1 единица Godot** по X и Z |
| 1 лептон | 1/256 единицы |
| Ось вверх | +Y |
| Клетка (x, y) симуляции | Godot (x + 0,5, 0, y + 0,5) — центр клетки |
| Высота уровня рельефа (визуальная) | 0,4 единицы (подбираем на глаз; в правилах высоты появятся в M7) |

Перевод симуляции в Godot — только в клиенте (`SimToGodot` из M0 дополняется высотой).

### 4.3. Рендер-настройки

Все параметры — в ресурсе `Environment` на климат (`game/assets/environments/winter.tres`) и в `DirectionalLight3D`. Меняются без кода.

| Элемент | Настройка | Зачем |
|---|---|---|
| Рендерер | Forward+ | SSAO, качественные тени, glow |
| Солнце | `DirectionalLight3D`, тени вкл., 2 каскада (сцена неглубокая из-за ортокамеры), мягкость (`shadow_blur`) | Мягкие тени как на референсе |
| Направление солнца | Сверху-слева-спереди относительно камеры, как в RA2 (тени падают вправо-вниз на экране) | Узнаваемость |
| Окружающий свет | Цвет неба, энергия под климат | Холодный зимний оттенок |
| SSAO | Вкл., радиус ~0,5 клетки | «Объём» у оснований зданий и деревьев |
| SSIL | Выкл. на старте (дорого), пробуем на витрине | — |
| Glow | Вкл., порог высокий | Только для будущих эффектов |
| Tonemap | Filmic или AgX (сравниваем) | Мягкие светлые участки на снегу |
| Цветокоррекция | `Adjustments` + 3D LUT (`.png` 32³) | Основной инструмент «настроения» климата |
| Туман | Лёгкий depth fog | Глубина у верхнего края экрана |
| Сглаживание | MSAA 2× или TAA (сравниваем на ортокамере), FXAA как запасной | Чистые края моделей |

**Бюджет:** 60 FPS при 1080p на MacBook с M1 для витрины M1 (≈ 200 деревьев, 10 зданий, 20 танков).

### 4.4. Рельеф

**Данные для M1:** карта 64×64 клетки (как в M0). Для витрины рельеф и маски задаются **вручную в коде витрины** (несколько холмов, дорога). Формат карты — в M7.

**Реализация (шаг 3):** высоты и вся математика (высота в точке, нормали, пересечение луча) — в чистом классе `TerrainHeights` без Godot, покрытом тестами xUnit (по образцу `MinimapMath`); меш строит `TerrainBuilder`.

**Меш (`TerrainBuilder`):**
- Сетка вершин в углах клеток: (64+1)×(64+1). Высота вершины — из массива высот (визуальные уровни × 0,4).
- Разбиение на **чанки 16×16 клеток** — меньше перерисовки и проще отсечение.
- Нормали — по соседним вершинам (сглаженные).
- UV0 — мировые координаты XZ (для тайлинга текстур), UV1 — координаты в маске всей карты.

**Шейдер смешивания `terrain_splat.gdshader`:**

| Вход | Что |
|---|---|
| 4 слоя | Снег, трава, грязь, дорога — у каждого albedo, normal, roughness (в `Texture2DArray`) |
| Маска | RGBA-текстура размера карты (64×64 пикселя → билинейная): R = трава, G = грязь, B = дорога, остаток = снег |
| Смешивание | По маске + **height blend** (слой с большей «высотой» текстуры побеждает на границе) — естественные рваные края вместо размытых |
| Тайлинг | Каждый слой — свой масштаб; против повторов — поворот UV по шуму |
| Наклон | На крутых склонах подмешиваем грязь/камень автоматически |

**Текстуры земли:** бесшовные 1024×1024, AI-генерация или CC0 (Poly Haven, ambientCG — CC0). Каждая запись — в реестре ассетов.

### 4.5. Декорации

- `PropScatter` раскладывает деревья и мелочь по маске плотности с **отдельным визуальным ГСЧ** (не симуляционным — визуал не должен трогать игровую случайность, см. M0, 4.5).
- `MultiMeshInstance3D` на каждый тип декорации и каждый чанк.
- Деревья: 2–3 вида елей, случайный поворот и масштаб ±15%.
- Мелочь: камни, сугробы, пни, столбы, заборы.
- **В M1 декорации чисто визуальные**, проходимость не меняют (это M2/M7).

### 4.6. Цвет команды

- Каждая модель техники и здания имеет **маску цвета команды**: отдельная текстура (канал R) или вершинный цвет, на выбор по результатам сравнения генераторов.
- Шейдер `team_color.gdshader` (на основе стандартного PBR): `albedo = mix(albedo, albedo_gray * team_color, mask)` — смешиваем по яркости исходника, чтобы сохранить детали и потёртости.
- Цвет команды задаётся параметром экземпляра (`instance uniform vec3 team_color`) — один материал на все команды.
- Палитра команд RA2-стиля (красный, синий, жёлтый, зелёный, оранжевый, фиолетовый, бирюзовый, розовый) — в отдельном ресурсе.

### 4.7. Стандарты моделей

Выносятся в отдельный документ `docs/art/model_standards.md`. Ключевое:

| Параметр | Стандарт |
|---|---|
| Формат | glTF 2.0 бинарный (`.glb`) |
| Масштаб | 1 клетка = 1 единица. Средний танк ≈ 0,8 клетки в длину; здание 2×2 занимает 2×2 единицы |
| Оси | +Y вверх, «перёд» модели смотрит в **−Z** (стандарт Godot) |
| Точка опоры (pivot) | Техника — центр основания на земле. Здание — центр футпринта на земле |
| Трансформации | Применены (масштаб 1, поворот 0) |
| Имена узлов | `hull`, `turret`, `barrel`, `muzzle_0..N` (точки выстрела, пустые узлы), `team_mask` (если вершинным цветом) |
| Башня | Отдельный узел `turret`, pivot — в оси вращения |
| Материалы | PBR: albedo, normal, ORM (occlusion/roughness/metallic в одной текстуре) |
| Текстуры | 1024² техника, 2048² большие здания; `.png` в исходниках, Godot сжимает (VRAM compression) |
| LOD | LOD0 + LOD1 (~50%) — для отдаления; Godot умеет автоматический LOD, сравниваем |
| Бюджет полигонов | Пехота ≤ 1,5k, техника ≤ 8k, здание ≤ 20k треугольников (LOD0) |

### 4.8. Пайплайн ассетов

```
1. Концепт        AI-картинка (вид 3/4, нейтральный фон) → assets_src/concepts/<id>/
2. Генерация 3D   AI-генератор → assets_src/generated/<id>/<сервис>/
3. Нормализация   blender --background --python tools/blender/rts_pipeline.py -- \
                    --input <raw> --id <id> --kind vehicle|building|prop
                  → нормализация → разделение на части → маска → LOD → .blend + .glb
4. Ручная доводка (при необходимости) в Blender → повтор шага 3 с флагом --from-blend
5. Проверка       rts_validate.py → отчёт: масштаб, оси, имена, бюджет, материалы
6. Импорт         .glb → game/assets/models/<kind>/<id>/  (Godot импортирует сам)
7. Реестр         запись в docs/assets_registry.md
```

**Blender-скрипты:**

| Скрипт | Что делает |
|---|---|
| `rts_normalize.py` | Удаляет мусор (камеры, лишние источники света), объединяет меши, ставит pivot, масштабирует к целевому размеру по `--kind` и `--footprint`, разворачивает «перёд» в −Z, применяет трансформации |
| `rts_split_parts.py` | Отделяет башню и ствол: по вершинной группе / по выделению из .blend / по высотному срезу (эвристика для генераций без разметки) |
| `rts_team_mask.py` | Строит маску по цвету исходной текстуры (заданный диапазон оттенков → маска) или проверяет готовую |
| `rts_lod.py` | Decimate до LOD1 |
| `rts_export.py` | Экспорт `.glb` с нужными флагами (Y-up, применённые модификаторы, без анимаций, если их нет) |
| `rts_validate.py` | Проверка по стандартам, отчёт в консоль и JSON |

**Версия Blender** фиксируется в `tools/blender/README.md` (текущая LTS). Скрипты запускаются без GUI, поэтому их можно гонять пачкой.

### 4.9. Сравнение AI-генераторов 3D

**Набор для теста** (одинаковый для всех сервисов, с одинаковыми концептами):

| Объект | Почему он |
|---|---|
| Здание 1: реактор Союза | Сложная форма, трубы, мелкие детали |
| Здание 2: казармы Союза | Простая коробка с крышей — проверка «чистоты» |
| Танк 1: тяжёлый танк | Нужна отделимая башня |
| Танк 2: тесла-танк | Нестандартная форма, катушка |

**Кандидаты:** Meshy, Tripo, Hunyuan3D (и, если появится сильный новый, — он).

**Критерии (оценка 1–5):**

| Критерий | Как оцениваем |
|---|---|
| Похожесть на концепт | На глаз, рядом с концептом |
| Чистота геометрии | Нет дыр, «каши» и слипшихся деталей |
| Текстура | Чёткость, отсутствие запечённого света и теней |
| Отделимость башни | Сколько ручной работы |
| Вид с нашей камеры | **Главный критерий:** рендер в Godot под углом RA2 на реальном зуме |
| Полигоны | Укладывается в бюджет после decimate |
| Лицензия | Можно ли публично распространять результат на нашем тарифе |
| Цена и скорость | Стоимость одной модели, время |

### 4.13. Анимационный пайплайн

**Принцип:** анимации — только на стороне клиента. Симуляция сообщает состояние и события (угол корпуса и башни, скорость, `WeaponFired`, `UnitDied`, стадия постройки), отображение решает, как это выглядит. На детерминизм анимации не влияют.

**Техника — процедурно, кодом (`VehicleAnimator`):**

| Что | Как | Требование к модели |
|---|---|---|
| Поворот корпуса и башни | Поворот узлов `hull` / `turret` по углам (в M1 — визуальные, с M2 — из симуляции) | Отдельные узлы, pivot на оси вращения |
| Отдача | Узел `barrel` отъезжает назад на 10–20 % длины за ~0,08 с и возвращается за ~0,3 с (кривая в коде) | Отдельный узел `barrel` |
| Гусеницы | Прокрутка UV текстуры гусениц по скорости (параметр шейдера) | Гусеницы — отдельный материал или UV-остров |
| Колёса | Вращение узлов `wheel_*` по скорости | Узлы `wheel_0..N` |
| Покачивание, наклон | Небольшой крен и тангаж при старте, торможении и повороте; позже — по рельефу (M7) | — |
| Вспышка, дым, гильзы | Частицы `GPUParticles3D` в узлах `muzzle_N` | Пустые узлы `muzzle_0..N` |

**Здания — шейдеры, частицы и простые узловые анимации (`BuildingAnimator`):**

| Что | Как | Требование к модели |
|---|---|---|
| Постройка (вырастание) | Шейдер `build_up.gdshader`: проявление снизу вверх по высоте с подсвеченной кромкой, длительность — из стадии постройки | — |
| Рабочие анимации | Вращение узлов `spin_*` (радар, вентиляторы), частицы дыма в узлах `smoke_*`, мигание огней в `light_*` (emission) | Узлы с этими префиксами |
| Особые движения (ворота завода) | `AnimationPlayer` с ключами в Blender, экспорт в `.glb` вместе с моделью. Имена клипов: `open`, `close`, `active` | Клипы с этими именами |
| Повреждения (заготовка для M4) | Частицы огня и дыма в узлах `damage_*`, усиление при снижении HP | Узлы `damage_*` |

**Пехота — скелет + Mixamo + ретаргетинг:**

1. **Модель** — человекоподобная, A- или T-поза, ≤ 1,5k треугольников (стандарт 4.7).
2. **Скелет** — автоматически через Mixamo (или авториггинг генератора, если качество лучше).
3. **Клипы** — из библиотеки Mixamo: `idle`, `walk`, `run`, `shoot`, `prone`, `prone_shoot`, `die_0..2`. Лицензия Mixamo разрешает использование в играх; источник фиксируется в реестре ассетов.
4. **Ретаргетинг** — в Godot через `SkeletonProfileHumanoid`: все клипы ставятся на любой человекоподобный скелет, библиотека анимаций одна на всю пехоту.
5. **Управление** — `AnimationTree` со state machine: стоит / идёт / бежит / стреляет / лежит / умирает, переходы по состоянию юнита из симуляции.

**Производительность пехоты.** Цель — **200 анимированных пехотинцев на экране при 60 FPS** (Mac M1, 1080p).

| Вариант | Когда |
|---|---|
| Скелетная анимация + LOD (упрощённый скелет и меньше обновлений вдали) | По умолчанию |
| Vertex animation textures (анимация «запечена» в текстуру, рисуется инстансингом) | Если вариант по умолчанию не держит цель |

Решение по варианту — по замеру на шаге 11 (раздел 5).

**Новые требования к моделям** дописываются в `docs/art/model_standards.md`: узлы `wheel_*`, `spin_*`, `smoke_*`, `light_*`, `damage_*`, имена клипов, поза пехоты.

## 8. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| AI-генераторы дают «кашу» на технике (особенно отделимая башня) | Высокая | Генерировать корпус и башню раздельно; ручная доводка в Blender; запасной вариант — CC0-модели + кит-башинг |
| Качество не дотягивает до референса | Средняя | Вердикт с конкретным списком доработок; план Б — упор на освещение и шейдеры (они дают ~половину эффекта), модели проще, но стильные |
| Лицензия генератора не позволяет публичное распространение | Средняя | Проверяем условия **до** сравнения, отсеиваем сервисы без такого права |
| Ортокамера + тени: «плавание» и мерцание теней при скролле | Средняя | Привязка каскадов к сетке текселей (stable shadows), подбор `shadow_bias` |
| Мерцание тонких деталей (заборы, ветки) на ортокамере | Средняя | MSAA/TAA, mipmaps, толщина деталей по стандарту |
| SSAO на ортокамере выглядит неверно | Низкая | Подбор радиуса; запасной вариант — запечённый AO в текстурах моделей |
| Пехота со скелетом недостижима генераторами | Высокая | Решение в этой вехе: упрощённые модели + процедурная анимация или ригинг через автоматические сервисы (Mixamo и аналоги, с проверкой лицензии) |
| Blender в CI ставится долго | Средняя | Проверка конвейера локальным скриптом, в CI — только `rts_validate.py` на готовых `.glb` |
| Git LFS: квота GitHub | Средняя | Сырые генерации храним выборочно, в LFS только используемое; следим за объёмом |
