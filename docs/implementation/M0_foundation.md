## 1. Цель и результат

**Цель:** построить детерминированное ядро симуляции, на котором дальше будет стоять вся игра: мультиплеер, повторы, боты, отладка. После M0 правила детерминизма зашиты в код и проверяются автоматически, а не держатся на дисциплине.

**Что будет работать в конце вехи:**

1. Решение .NET из трёх проектов: симуляция (чистый C#), тесты, Godot-клиент.
2. Симуляция тикает с фиксированной частотой, принимает команды, двигает тестовые юниты.
3. Математика с фиксированной точкой, детерминированный ГСЧ, контрольная сумма состояния.
4. Повтор: запись команд партии в файл и воспроизведение с проверкой контрольных сумм.
5. Godot-клиент: плоская карта, тестовые юниты-кубики, клик — команда «двигаться», плавная интерполяция, отладочная панель.
6. CI на GitHub: тесты проходят на macOS, Windows и Linux и дают **одинаковые контрольные суммы**.

**Как это выглядит для игрока:** серое поле, на нём несколько кубиков. Клик по полю — кубики едут в точку. В углу — номер тика, FPS, контрольная сумма. Ничего красивого, но под капотом — тот же механизм, что будет в финальной игре.

## 4. Технические решения

### 4.1. Целевая платформа .NET

- Все проекты: `net8.0` — минимум для Godot 4.7 .NET и LTS-версия.
- Собираем **.NET SDK 10** (он умеет собирать `net8.0`).
- Тестам разрешено запускаться на более новой среде (`RollForward=Major`), чтобы не ставить отдельно рантайм 8.0.
- Общие настройки в `Directory.Build.props`: `LangVersion=latest`, `Nullable=enable`, `TreatWarningsAsErrors=true`, `ImplicitUsings=disable` в симуляции (чтобы видеть каждый используемый API).

### 4.2. Защита детерминизма на уровне компилятора

Симуляция **физически не может** ссылаться на Godot: у проекта `Rts.Simulation` нет такой зависимости.

Для остального подключаем анализатор **Microsoft.CodeAnalysis.BannedApiAnalyzers** только к `Rts.Simulation`. В `BannedSymbols.txt`:

| Запрещено | Почему | Чем заменить |
|---|---|---|
| `float`, `double`, `decimal` | Разные результаты на разных процессорах (кроме `decimal`, но держим единообразие) | `Fixed`, `int`, `long` |
| `System.Math`, `System.MathF` | Работают с `double` / `float` | `IntMath`, методы `Fixed` |
| `System.Random`, `Random.Shared` | Алгоритм не гарантирован между версиями .NET | `DeterministicRandom` |
| `DateTime.Now`, `UtcNow`, `Stopwatch`, `Environment.TickCount` | Время недетерминировано | Номер тика |
| `Parallel`, `Task.Run`, `ThreadPool` | Порядок выполнения недетерминирован | Последовательный код |
| `Guid.NewGuid` | Случайный | `EntityId` из счётчика |
| `HashCode`, `object.GetHashCode` для строк | Рандомизируется при каждом запуске процесса | Собственный хеш |
| Перечисление `Dictionary`/`HashSet` | Порядок не гарантирован | `List`, сортировка по ID, `SortedDictionary` |

**Проверка на шаге 1:** убеждаемся, что анализатор действительно ловит ключевые слова `float`/`double`. Если нет — запасной вариант: тест, который сканирует исходники симуляции и падает при нахождении запрещённых токенов.

### 4.3. Фиксированная точка: `Fixed`

| Параметр | Значение |
|---|---|
| Хранение | `long` (64 бита) |
| Дробная часть | 16 бит (формат Q47.16) |
| Шаг | 1/65536 ≈ 0,000015 |
| Диапазон | ≈ ±140 триллионов — с огромным запасом |

**Операции и правила округления** (фиксируются, потому что от них зависит совпадение результатов):

| Операция | Реализация | Округление |
|---|---|---|
| `+`, `-` | Сложение `long` | Точно |
| `*` | `(Int128)a * b >> 16` | Вниз (к −∞), арифметический сдвиг |
| `/` | `((Int128)a << 16) / b` | К нулю (стандарт C#) |
| Деление на 0 | Исключение | Это ошибка в логике, а не игровая ситуация |
| `Sqrt` | Целочисленный побитовый корень на `UInt128` | Вниз |
| Сравнения, `Min`, `Max`, `Abs`, `Clamp` | Над `long` | Точно |

**Создание:** `Fixed.FromInt(5)`, `Fixed.FromRaw(...)`, `Fixed.FromRatio(3, 2)` (= 1,5). **Нет** конструкторов из `float`/`double` в симуляции.

**Перевод в `float` для отображения** — только в клиенте (расширение в `Rts.Client`), симуляция такого метода не имеет.

**Переполнение:** в Debug-сборке промежуточные результаты проверяются (`checked`), в Release — нет. Переполнение считается ошибкой и ловится тестами.

**`IntMath`** — целочисленные помощники: `Abs`, `Min`, `Max`, `Clamp`, `Sign`, `Sqrt(long)`, `DivFloor`.

### 4.4. Координаты

| Тип | Что | Единица |
|---|---|---|
| `WorldPos` | Точная позиция в мире: `int X, Y` | Лептон: **256 лептонов = 1 клетка**, как в RA2 |
| `CellPos` | Клетка карты: `int X, Y` | Клетка |

- Перевод: `CellPos = WorldPos / 256` (с округлением вниз через `IntMath.DivFloor`, чтобы отрицательные координаты считались правильно), центр клетки = `cell * 256 + 128`.
- Высота (`Z`) добавится вместе с рельефом в M7.
- Скорости — в лептонах за тик (`int` или `Fixed`, если нужна дробная).

### 4.5. Детерминированный ГСЧ: `DeterministicRandom`

- Алгоритм **PCG32 (XSH-RR)**: 64-битное состояние, 32-битный результат. Простой, быстрый, хорошо изучен, результат определён спецификацией, а не реализацией .NET.
- Seed задаётся в `SimulationSettings` (в сети — от сервера, в повторе — из файла).
- Методы: `NextUInt()`, `NextInt(maxExclusive)` (без смещения, через отбрасывание), `NextInt(min, maxExclusive)`, `NextBool()`, `NextFixed()` в [0, 1).
- Состояние ГСЧ входит в контрольную сумму.
- **Один экземпляр на симуляцию.** Клиент и отображение используют **свой**, отдельный генератор для визуальных случайностей (разброс искр и т. п.) — чтобы визуальные эффекты никогда не сдвигали игровую случайность.

### 4.6. Мир и сущности

- `EntityId` — `int`, выдаётся счётчиком мира по возрастанию, никогда не переиспользуется.
- Сущности хранятся в `List`, **отсортированном по ID** (новые добавляются в конец — порядок сохраняется автоматически). Поиск по ID — бинарный поиск.
- Удаление: сущность помечается мёртвой, физически удаляется в конце тика. Внутри тика список не меняется.
- **`TestUnit`** — единственный тип сущности в M0: `Id`, `Owner`, `Position`, `MoveTarget?`, `Speed` (лептонов/тик).
- `World` хранит: текущий тик, сущности, счётчик ID, ГСЧ.

### 4.7. Команды

```
Command (абстрактная)
├── PlayerId        int     — кто отдал
├── ExecuteTick     int     — на каком тике исполнить
├── Sequence        uint    — порядковый номер у этого игрока
└── Type            byte    — тип для сериализации

SpawnTestUnitCommand   : Position              — отладочная, создать юнит
MoveUnitsCommand       : EntityId[], Target    — двигаться в точку
```

**Очередь команд (`CommandQueue`):**
- Команды раскладываются по тикам исполнения.
- На тике команды применяются в **строгом порядке**: `(PlayerId, Sequence)`. Это гарантирует одинаковый результат, даже если по сети они пришли в разном порядке.
- Команда на уже прошедший тик — ошибка (в сети будет обрабатываться отдельно).

**Проверка команды** при применении: юниты существуют, принадлежат игроку, цель в пределах карты. Невалидная команда **молча и одинаково у всех** игнорируется (или частично: из списка юнитов отбрасываются чужие).

**Бинарный формат** (little-endian, через `BinaryPrimitives` — не зависит от процессора):

```
u8   type
i32  playerId
i32  executeTick
u32  sequence
...  полезная нагрузка (своя для каждого типа)
     MoveUnits:     u16 count, i32 × count ids, i32 x, i32 y
     SpawnTestUnit: i32 x, i32 y
```

Этот же формат пойдёт в сеть (M9) и в повторы.

### 4.8. Тик симуляции

Порядок внутри `Simulation.Step()` — **фиксированный**, меняется только осознанно:

```
1. Взять команды для тика T, отсортировать, проверить, применить
2. Системы по порядку (в M0 — только MovementSystem)
3. Удалить мёртвые сущности
4. T = T + 1
5. Посчитать контрольную сумму (если T кратен HashInterval)
```

**`MovementSystem`:** юнит с целью движется к ней на `Speed` лептонов за тик. Направление: вектор (dx, dy), длина — `Fixed.Sqrt`, шаг — пропорционально. Если до цели меньше шага — встаёт точно в цель и сбрасывает её.

**События (`SimEvent`):** в M0 — `UnitSpawned`, `UnitMoveStarted`, `UnitArrived`. Список событий тика отдаётся клиенту и очищается на следующем тике. Клиент по ним проигрывает звуки и эффекты (в M0 — просто пишет в лог).

**Параметры (`SimulationSettings`):**

| Параметр | Значение в M0 |
|---|---|
| `TicksPerSecond` | 15 (подбираем позже, см. открытые вопросы в [03](../03_architecture.md)) |
| `LeptonsPerCell` | 256 (константа) |
| `MapSizeCells` | 64 × 64 |
| `Seed` | задаётся при старте |
| `HashInterval` | 1 (каждый тик — в M0 это дёшево) |

### 4.9. Контрольная сумма: `StateHasher`

- Алгоритм **FNV-1a 64** — простой, быстрый, без зависимостей.
- Хешируются, в фиксированном порядке: номер тика, состояние ГСЧ, счётчик ID, число сущностей, затем каждая сущность по возрастанию ID (все поля).
- Числа пишутся в little-endian через `BinaryPrimitives`.
- **Правило:** любое новое поле состояния обязано попасть в хеш. Проверяется тестом (см. раздел 6).

### 4.10. Повторы

**Формат файла** `.rtsreplay`:

```
magic          "RTSR" (4 байта)
formatVersion  u16
simVersion     u32          — версия правил симуляции
settings       seed, ticksPerSecond, mapSize
commandCount   u32
commands       × commandCount  (формат 4.7)
checksumCount  u32
checksums      × (i32 tick, u64 hash) — для проверки
```

- **`ReplayRecorder`** — копит все применённые команды и контрольные суммы во время игры.
- **`ReplayPlayer`** — создаёт симуляцию с теми же настройками, подаёт команды по тикам, сверяет суммы. Результат: «совпало» или «первое расхождение на тике N».
- Работает без Godot — используется и в тестах, и в будущем в CI, и в инструментах рассинхрона ([13_tools.md](../13_tools.md)).

### 4.11. Godot-клиент

**Дерево сцены `Main.tscn`:**

```
Main (Node3D)
├── SimulationHost      — C#: владеет Simulation, крутит тики
├── CameraRig
│   └── Camera3D        — ортографическая, временный угол (настоящий — в M1)
├── Sun (DirectionalLight3D)
├── Ground (MeshInstance3D)  — плоскость 64×64 клетки с сеткой
├── UnitsRoot (Node3D)  — визуалы юнитов (кубики)
└── DebugOverlay (CanvasLayer)
    └── Label           — тик, тиков/с, FPS, сущности, хеш
```

**Цикл с фиксированным шагом (`SimulationHost._Process`):**

```
accumulator += delta × скорость_игры
пока accumulator >= длительность_тика и тиков_за_кадр < 5:
    отдать накопленные команды игрока в очередь (на тик T + 1)
    simulation.Step()
    accumulator -= длительность_тика
alpha = accumulator / длительность_тика   — для интерполяции
```

Ограничение «не больше 5 тиков за кадр» защищает от лавины, если кадр завис.

**Отображение:**
- Для каждой сущности — `UnitView` (кубик), из пула.
- Позиция = интерполяция между позицией на прошлом и текущем тике по `alpha`. Перевод лептонов в метры Godot: 1 клетка = 1 единица.
- Появление и исчезновение — по событиям симуляции.

**Ввод (отладочный):**

| Действие | Что делает |
|---|---|
| Левый клик по земле | `MoveUnitsCommand` для всех юнитов игрока 0 |
| Shift + левый клик | `SpawnTestUnitCommand` в точку |
| P | Пауза |
| N (на паузе) | Один тик |
| `+` / `-` | Скорость игры |
| F5 | Сохранить повтор текущей сессии в `user://replays/` |
| F9 | Перезапустить из последнего повтора (визуальная проверка) |

Точка клика переводится из координат Godot в лептоны в клиенте (`float` → `int`). Это безопасно: в команду уходят уже целые числа, и у всех участников они одинаковые.

**Godot и решение:** `project.godot` указывает на общее решение в корне (`dotnet/project/solution_path`), `Rts.Client.csproj` ссылается на `Rts.Simulation` через `ProjectReference`.

### 4.12. CI

`.github/workflows/ci.yml`, на каждый push и pull request:

| Задача | ОС | Что |
|---|---|---|
| `test` | ubuntu, macos, windows | `dotnet test` по `Rts.Simulation.Tests` |
| `build-client` | ubuntu | `dotnet build` клиента (проверка, что компилируется) |

**Кросс-платформенный детерминизм** проверяется «золотыми» тестами (раздел 6): на всех трёх ОС ожидаются одни и те же зашитые в тест значения. Если Windows посчитает иначе, чем macOS, тест упадёт.

### 4.13. Соглашения по коду

- C#: file-scoped namespaces, один тип — один файл, `sealed` по умолчанию.
- Комментарии и имена в коде — **на английском** (репозиторий публичный). Документация — на русском.
- Симуляция не бросает исключения в нормальной игре: исключение = баг.
- Публичные структуры-значения (`Fixed`, `WorldPos`) — `readonly struct`.

### 4.14. Работа в git

- Работаем в ветке `m0/foundation`.
- **Один шаг из раздела 5 — минимум один коммит** с понятным описанием.
- В конце — pull request в `main`, слияние после зелёного CI.

## 5. Шаги реализации

Каждый шаг заканчивается проверяемым результатом. Следующий шаг не начинается, пока предыдущий не готов.

| № | Шаг | Результат | Готово, когда |
|---|---|---|---|
| 0 | **Окружение** | .NET SDK 10, Godot 4.7.2 .NET в `/Applications` | `dotnet --info` работает, Godot открывается |
| 1 | **Каркас решения** | `RtsGame.sln`, `Directory.Build.props`, `.editorconfig`, три пустых проекта, анализатор | `dotnet build` и `dotnet test` проходят; `double` в симуляции даёт ошибку сборки |
| 2 | **`Fixed` и `IntMath`** | Типы с операциями и правилами округления из 4.3 | Модульные тесты на все операции, включая отрицательные числа и границы |
| 3 | **`DeterministicRandom`** | PCG32 | Тест на эталонную последовательность |
| 4 | **Мир и сущности** | `EntityId`, `TestUnit`, `World`, `WorldPos`, `CellPos` | Тесты: порядок, удаление, поиск по ID |
| 5 | **Команды** | Базовый класс, 2 команды, очередь, сериализатор | Тесты: порядок применения, сериализация туда-обратно, отбрасывание невалидных |

## 6. Тесты

### Модульные

| Область | Что проверяем |
|---|---|
| `Fixed` | Сложение, вычитание, умножение и деление с округлением по правилам 4.3; отрицательные числа; `Sqrt` на точных квадратах и между ними; `FromRatio`; сравнения |
| `IntMath` | `DivFloor` для отрицательных, `Sqrt` на больших числах |
| `DeterministicRandom` | Эталонная последовательность; `NextInt` всегда в диапазоне; два генератора с одним seed дают одно и то же |
| `World` | ID растут, не переиспользуются; порядок обхода = порядок ID; удаление в конце тика |
| Команды | Сериализация туда-обратно для каждого типа; порядок `(PlayerId, Sequence)`; невалидные игнорируются |
| `MovementSystem` | Точное прибытие; движение по диагонали; нулевое расстояние |
| `StateHasher` | Изменение каждого поля сущности меняет хеш |

### Детерминизм

| Тест | Как |
|---|---|
| **Два прогона** | Один и тот же сценарий из 1000 тиков со случайными (по seed) командами → одинаковые суммы на каждом тике |
| **Порядок прихода команд** | Те же команды, добавленные в очередь в перемешанном порядке → тот же результат |
| **Повтор** | Сценарий → запись → чтение из байтов → проигрывание → суммы совпадают |
| **Сохранение ГСЧ** | Состояние ГСЧ после N вызовов одинаково в двух прогонах |

### «Золотые» значения (кросс-платформенные)

Фиксированные сценарии, у которых результат **зашит в тест**:

- первые 10 чисел `DeterministicRandom` при seed 42;
- 20 заранее выбранных операций `Fixed` (умножение, деление, корень) с точными ожидаемыми `raw`-значениями;
- контрольная сумма после 1000 тиков эталонного сценария.

Значения снимаются один раз на Mac при первом прогоне и фиксируются. После этого CI на Windows и Linux обязан получить те же числа. Любое изменение правил симуляции, меняющее эти значения, — осознанное и сопровождается обновлением эталона в том же коммите с объяснением.

### Защита хеша

Тест через рефлексию проверяет, что все поля `TestUnit` и `World` учтены в `StateHasher` (список «учтённых» полей ведётся явно). Добавил поле и забыл про хеш — тест падает.
