**Корень — `game/data/`.** Данные лежат внутри Godot-проекта, потому что клиенту они нужны в сборке (в настройках экспорта — фильтры `*.yaml`, `*.rtsmap`). Тесты, Arena и сервер читают их по пути от корня репозитория.

├── factions/
│   ├── factions.yaml         список фракций и стран                M3, M11
│   ├── union/                buildings, units, weapons             M3, M4
│   ├── alliance/                                                   M11
│   └── cult/                                                       M11
├── combat/                   armor, warheads, projectiles          M4
│                             + veterancy                           M11
├── ai/
│   ├── difficulty.yaml       уровни (M5 — medium, M8 — все 4)
│   ├── personalities/                                              M8
│   ├── buildorders/<faction>/*.yaml                                M5, M8
│   └── compositions/<faction>.yaml                                 M5

## 4. Игроки и идентификаторы

| Что | Правило |
|---|---|
| `PlayerId 0` | **Нейтральный игрок** (`Neutral`): существует в каждой партии, никем не управляется, владеет нейтральными зданиями и объектами карты, не участвует в условиях победы |
| `PlayerId 1…8` | Игроки (люди и боты). В отладочном клиенте M0–M4 локальный игрок — `1` |
| Союзники | Игроки одной команды описания партии (`MatchPlayer.Team`; M8, шаг 11, `simVersion` 40). Видят то, что видит союзник. Союзник — не враг: не цель, его пехоту не давят, приказ атаки по нему отклоняется, принудительная атака — можно, его попадания не поднимают «база атакована». Без описания партии игрок один |
| `EntityId` | Общий счётчик мира для юнитов, зданий и снарядов (M4); растёт, не переиспользуется |
| Объекты карты | Свой счётчик ID (M7): деревья, заборы, мосты |
| Определения | В командах — индекс `u16` в каноническом порядке (по `id`), а не строка (M3) |

## 5. Порядок систем в тике

Единый порядок для всех вех. Веха, добавляющая систему, вставляет её в указанное место и обновляет этот список.

```
 1. VisibilitySystem — что появилось между тиками (здания карты, юниты тестов)   M4
 2. Команды тика T: сортировка (PlayerId, Sequence), проверка, применение      M0
 3. Супероружие: таймеры, запуски                                                M11
 4. Способности: телепорт, контроль разума, мутация, захват, вход в здания      M11
 5. PathRequestQueue — обработка в пределах бюджета                             M2
 6. PowerSystem                                                                  M3
 7. ProductionSystem                                                             M3
 8. BuildUpSystem — завершение вырастания зданий                                 M3
 9. HarvesterSystem — поиск руды, добыча, разгрузка                             M3
10. RepairSystem                                                                 M3
11. TargetingSystem → PursuitSystem → WeaponSystem → ProjectileSystem → DamageSystem   M4
12. Ветеранство                                                                  M11
13. MovementSystem: земля → вода → воздух; давка — CrushSystem при въезде в клетку   M2, M4, M11
14. SpatialIndex.Sync                                                           M2
15. Ящики, техздания                                                             M11
16. OreGrowthSystem (по интервалу)                                               M3
17. TechTree — пересчёт при изменении зданий                                     M3
18. VictorySystem — победа и поражение, в партии раз в 15 тиков                  M5
19. DeathSystem — клетки рухнувших открываются (+ выброс пассажиров и гарнизона в M11)   M4
20. VisibilitySystem                                                             M4
21. MatchStats — статистика тика, пока погибшие ещё в мире                       M5
22. Удаление мёртвых                                                             M0
23. Боты думают: читают состояние после тика T, выдают команды на T + 1          M5
24. T = T + 1, контрольная сумма (раз в HashInterval)                            M0
```

**Как сделано (M4, шаг 16):** порядок выше совпадает с `GameSimulation.Step()`. Гибель наступает в момент урона или давки (`DeathSystem.Kill` / `Destroy`). Пункт 19 в конце тика только открывает клетки рухнувших зданий. Продажа — команда, отдельной системы у неё нет.

**Как сделано (M5, шаг 15):** победа и поражение (`VictorySystem`) — после технологий, до открытия обломков: всё проигравшего падает и уходит из мира в том же тике. Статистика (`MatchStats`) читает события тика после видимости, пока погибшие ещё в мире: чьи они были. Боты думают после удаления погибших.

## 11. Git

- **Одна рабочая папка, работа прямо в `main`** (решение владельца 2026-10-21, заменяет правило «одна веха — одна ветка»). В проекте параллельно работают несколько сессий, и отдельные ветки требовали отдельных рабочих папок (git worktree), что неудобно для проверки. Ветки `m0/foundation` и `m1/visual-spike` остаются на GitHub как история.
- Один шаг плана — минимум один коммит. Каждый коммит — законченный и проверенный шаг: сборка без предупреждений, тесты зелёные.
- Коммитим **только свои файлы**: в рабочей копии могут лежать незакоммиченные правки других сессий.
- После push CI должен быть зелёным; красный CI на `main` чинится в первую очередь.
- Pull request не используем (решение 2026-10-21).
- Журнал выполнения в конце каждого плана обновляется вместе с кодом.

## 12. Символическое отображение

До финального визуала (последний этап, [16_roadmap.md](../16_roadmap.md)) игра отображается **символически**. Решение владельца 2026-10-21: сначала механика, внешний вид в конце.

1. **Видимое = правила.** Каждый элемент на экране соответствует механике; нет механики — нет картинки. Ничего «для красоты», что можно принять за правило: если нарисована вода, по ней нельзя ходить.
2. **Простые формы, плоские цвета, цвет команды.** Юниты — примитивы, форма по классу: пехота — маленькая капсула, техника — коробка с «носом», показывающим направление, авиация — ромб над землёй. Здания — коробки по футпринту.
3. **Земля — плоский цвет по типу клетки из симуляции:** обычная земля — светлая, дорога — тёмно-серая, бездорожье — коричневое, деревья — тёмно-зелёные столбики, скалы — серые блоки, вода — синяя, руда — жёлтые ромбы. Непроходимое выглядит непроходимым.
4. **Каждый элемент карты появляется вместе со своей механикой.** Холмы витрины M1 (шаг 3) были исключением до M7: на шаге 9 они убраны, и рельеф любой карты рисуется только по высотам правил.
5. **Читаемость прежде всего:** при необходимости — подписи и отладочные оверлеи (проходимость, пути, зоны обзора).
6. Камера RA2, свет и тени из M1 остаются: они помогают читать сцену и ничего не обещают.
7. **Финальный арт — последний этап**, по плану M1 (шаги 4–14) и M11.

## 13. Тесты: быстрые и долгие

- **Быстрый набор** — всё, что не помечено `Category=Slow` или `Category=Arena`. Он идёт на каждый push в Debug и Release; бюджет — около 3 минут на конфигурацию.
- **`Slow`** — тест, который играет партию на настоящей карте минутами игрового времени или гонит Arena. В Debug симуляция в разы медленнее, поэтому такие тесты идут только в Release — на трёх ОС, детерминизм проверяется там. Новый долгий тест сразу получает `[Trait("Category", "Slow")]`.
- **`Arena`** — 20 партий бот-против-бота по 40 минут (M5), отдельный шаг CI в Release.
- **Матрицы Arena** (`acceptance.yaml`) — не тесты: отдельный процесс раз в сутки (`.github/workflows/arena.yml`).
